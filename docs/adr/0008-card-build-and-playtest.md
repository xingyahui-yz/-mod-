# Card 构建与实机验证路线

> 状态：已接受 · 日期：2026-10-02 · 来源：用户 + Codex `/grill-with-docs` 会话

Mod Studio 已支持 Card 编辑、保存、C# 生成、测试预检和启动游戏，但当前生成器仍使用 `RitsuMod` 命名空间，启动器不会编译或部署项目。由于 STS2 构建接口随已安装游戏版本变化，先针对用户当前安装版本完成一个小型兼容性验证，再决定保留或迁移生成器与框架；不先假定某个社区框架对所有版本均兼容。

## 决策

- 产品主线是创作 STS2 Mod。首个交付闭环聚焦 Card；AI 卡面、打击音效和人物动作生成留到后续阶段。
- 第一阶段是兼容性验证：Windows 优先，检测用户实际安装的游戏版本；用一张普通、固定伤害的 Ironclad 攻击牌验证代码生成、构建、本地部署和实机对局。样例卡进入 Ironclad 普通卡池，不要求自定义卡面；用户在游戏内确认可以获得并造成预期伤害。
- 验证结果应沉淀为可复用的 Card 构建与部署流程。依赖缺失时提供可信来源和清晰安装指引，不由 Mod Studio 自动安装。尚未验证的游戏版本允许继续尝试，但必须明确提示其验证状态。
- 本地闭环完成后再实现发布：Mod Studio 准备 Workshop 发布工作区并调用 Mega Crit 官方上传器；上传前构建及包预检必须通过，实机验证作为强提醒但不阻断，最终上传需用户单独确认。发布工作区必须剥离 `.modstudio/`，遵循 [项目目录 ADR](./0003-local-project-structure.md) 的隔离约定。
- Workshop 发布流程与本地闭环同步设计，但不纳入本轮实现。

## 依据与备选

仓库当前 `CardData` 没有角色或卡池归属，Card 模板也只生成 `RitsuMod.Content.CardComponent` 子类；因此兼容性验证需要覆盖内容注册与卡池归属，而不能只验证 C# 能否编译。候选路线包括沿用当前接口、直接迁移到维护中的社区框架，或先做兼容性验证再选；选择验证优先，以免在未证实的游戏版本/API 契约上建设完整构建链。

游戏已提供内置 Mod 加载器；Mega Crit 官方上传器支持通过工作区命令创建或更新 Workshop 条目。参考：[官方 Mod 支持说明](https://steamcommunity.com/app/2868840/announcements/)；[官方 Workshop 上传器](https://github.com/megacrit/sts2-mod-uploader)；[RitsuLib 社区框架](https://github.com/BAKAOLC/STS2-RitsuLib)。

## 后果

- 首轮兼容性验证可能促成 Card 生成模板、角色卡池归属和项目构建产物模型的调整；兼容性必须以实际游戏版本验证结果为准。
- 未验证版本的构建可能失败或无法加载，因此产品需区分“构建成功”“部署成功”和“实机验证成功”，并保留可理解的版本警告。
- Workshop 上传属于独立的外部发布动作，不能由游戏启动或本地部署隐式触发。

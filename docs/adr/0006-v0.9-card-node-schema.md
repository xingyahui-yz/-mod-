# ADR-0006：v0.9 Card 节点 schema — 完全同构 trigger→effect 链 + Self/Any 前缀命名

> 状态：已接受 · 日期：2026-08-12 · 来源：`/grill-with-docs` 评审（2026-08-12，v0.8 合 main 后）
> 适用范围：v0.9 "卡牌接入节点编辑器" 的节点 schema 形态；连带 v0.9 Relic trigger 列表扩展

## 背景（Context）

v0.8 完成架构清理（评审 5 候选 3/5 ✅）后，v0.9 起点评估指向 **E1 卡牌接入节点图**。现有节点编辑器（`useNodeGraph` + `kinds.ts` + `RelicEditor.codegen`）是事件驱动模型（trigger→effect 链），与卡牌的语义形态是否同构需要先敲定。

v0.7 / v0.8 时 Card 仍为纯表单 + 实时预览；Codegen 是文本字段级（`generateCardCode` 用 Mustache 渲染）。问题：

1. **是否复用 trigger→effect 模型** — Card 与 Relic 是不是同一种"事件驱动实体"？
2. **trigger 表怎么拆分** — 大表 / 分表 / 共享？
3. **trigger 列表范围** — Card 真需要哪些 trigger？
4. **"卡自触发" vs "全局监听"** — `onDiscard` / `onExhaust` 两种语义形态要不要都在 Card 表里？

## 决策（Decision）

### 1. 完全同构 trigger→effect 链

Card 复用 Relic 的节点图模型：

- 一个 Card = 一个 trigger 节点 + 0..N 个 effect 节点 + 边
- `useNodeGraph(cardId, 'card', initial?)` 与 `useNodeGraph(relicId, 'relic', ...)` 同形
- codegen 复用 `collectStatements` BFS 逻辑（v0.5.2 起已稳定），共用 `EFFECT_KINDS` 表
- 模板差异：Card 模板 `cardTemplate.mustache`，Relic 模板 `relicTemplate.mustache`

### 2. TRIGGER_KINDS 大表 + `entity` 字段（A1）

`src/node-editor/kinds.ts`（或新建 `src/shared/kinds.ts`）维护**一张大表**，每条 trigger 定义加 `entity: 'card' | 'relic' | 'enemy' | 'event'` 字段：

```ts
export const TRIGGER_KINDS = {
  // Card 形态 1（卡自触发）
  onPlay:           { entity: 'card',  label: '使用卡牌',     methodName: 'OnPlay' },
  onSelfDraw:       { entity: 'card',  label: '抽到自身',     methodName: 'OnSelfDraw' },
  onSelfExhaust:    { entity: 'card',  label: '自身被消耗',   methodName: 'OnSelfExhaust' },
  onSelfDiscard:    { entity: 'card',  label: '自身被弃',     methodName: 'OnSelfDiscard' },
  // Relic 已有（v0.5.2 起）
  onCombatStart:    { entity: 'relic', label: '战斗开始',     methodName: 'OnCombatStart' },
  onCombatEnd:      { entity: 'relic', label: '战斗结束',     methodName: 'OnCombatEnd' },
  onTurnStart:      { entity: 'relic', label: '回合开始',     methodName: 'OnTurnStart' },
  onTurnEnd:        { entity: 'relic', label: '回合结束',     methodName: 'OnTurnEnd' },
  // Relic v0.9 新增（形态 2 全局监听）
  onAnyCardExhausted:  { entity: 'relic', label: '任意卡被消耗', methodName: 'OnAnyCardExhausted' },
  onAnyCardDiscarded:  { entity: 'relic', label: '任意卡被弃',   methodName: 'OnAnyCardDiscarded' },
} as const
```

UI 层（`NodeGraphCanvas` 工具栏 + `useNodeGraph.addNode`）按 `entity` 字段过滤：CardEditor 看不到 Relic trigger，反之亦然。

### 3. Self / Any 前缀命名约定（关键）

**Self 前缀 = 形态 1（卡自触发）**：`onSelfDraw` / `onSelfExhaust` / `onSelfDiscard` — 触发器绑定到**这张卡自己**的行为。

**Any 前缀 = 形态 2（全局监听）**：`onAnyCardExhausted` / `onAnyCardDiscarded` — 监听器订阅**任意卡**的事件，由装备它的实体（Relic）响应。

无前缀（`onPlay` / `onCombatStart` / `onTurnEnd`）= 默认形态（按上下文自明）。

这个命名约定的语义价值：codegen 看方法名就知"有没有事件参数" — `OnSelfExhaust` 收 `this`，`OnAnyCardExhausted` 收 `exhaustedCard` 参数。

### 4. validateGraph 新规则

`validateGraph` v0.9 起加一条规则：

```ts
// trigger 的 entity 字段必须匹配 graph 的 entityType
if (node.type === 'trigger' && triggerDef.entity !== graph.entityType) {
  return { ok: false, reason: `Trigger '${kind}' 不允许用于实体类型 '${entityType}'` }
}
```

避免"CardEditor 里不小心拖入了 `onCombatStart` Relic trigger"这类跨实体污染。

### 5. codegen 复用粒度

`collectStatements(graph: NodeGraph): string[]` **完全共用**（BFS 从 trigger.out 出发，遍历 effect 节点，渲染 C# 语句）。

模板层差异（`cardTemplate.mustache` vs `relicTemplate.mustache`）由 `generateCardCode` / `generateRelicCode` 各自包装。

### 6. EFFECT_KINDS 大表 + 实体绑定 effect 各占一条（走法 2）

**通用副作用**（dealDamage / healHp / gainBlock / applyBuff / applyDebuff / drawCards / gainEnergy）= **完全共享** — Card.OnPlay 和 Relic.OnCombatStart 生成相同的 C# 语句，EFFECT_KINDS 单条目。

**实体绑定 effect** = **各占一条**：
- Card 专属：`exhaustSelf` / `discardSelf` / `addCardToHand` / `addCardToDeck`（命名带 `Self` 后缀，C# 方法是 `ExhaustSelf()` 等）
- Relic 形态 2 专属：`exhaustCard` / `applyBuffToEventTarget` / `applyDebuffToEventTarget`（命名带 `Card` 或 `EventTarget` 后缀，C# 方法收 `targetCard` 参数）

走法 2 的核心：命名携带语义，codegen 机械翻译，不需要 `target` 字段推断。

```ts
export const EFFECT_KINDS = {
  // 通用副作用（共享）
  dealDamage:  { label: '造成伤害',    defaultData: { amount: 0, target: 'randomEnemy' } },
  healHp:      { label: '回复 HP',     defaultData: { amount: 0 } },
  gainBlock:   { label: '获得格挡',    defaultData: { amount: 0 } },
  applyBuff:   { label: '附加 buff',   defaultData: { buff: '', stacks: 1 } },
  applyDebuff: { label: '附加 debuff', defaultData: { buff: '', stacks: 1 } },
  drawCards:   { label: '抽牌',        defaultData: { amount: 1 } },
  gainEnergy:  { label: '获得能量',    defaultData: { amount: 1 } },
  // Card 专属（Self 后缀）
  exhaustSelf:    { entity: 'card',  label: '消耗自身',  defaultData: {} },
  discardSelf:    { entity: 'card',  label: '弃掉自身',  defaultData: {} },
  addCardToHand:  { entity: 'card',  label: '向手牌加牌', defaultData: { kind: '', amount: 1 } },
  addCardToDeck:  { entity: 'card',  label: '向牌堆加牌', defaultData: { kind: '', amount: 1 } },
  // Relic 形态 2 专属（Card / EventTarget 后缀）
  exhaustCard:            { entity: 'relic', label: '消耗被监听卡',     defaultData: {} },
  applyBuffToEventTarget: { entity: 'relic', label: '给被监听卡加 buff', defaultData: { buff: '', stacks: 1 } },
  applyDebuffToEventTarget: { entity: 'relic', label: '给被监听卡加 debuff', defaultData: { buff: '', stacks: 1 } },
} as const
```

**与 trigger 的关键区别**: `validateGraph` **不阻止**任何 effect 出现在任何实体节点图里。阻止的是"语义不匹配"（Card 节点图放 `exhaustCard` 是 bug，但 `exhaustSelf` 是 OK 的）— 责任交给 UI 层（添加 effect 节点时按 entityType 过滤 palette）和 codegen 时类型检查。

### 7. CardEditor UI 布局 — 走法 1（顶部表单横排 + 下部节点图 + 折叠预览）

Card 表单字段比 Relic 多（6 个 vs 5 个），且 cost/type/rarity/keywords 是**核心身份字段**（玩家先看 cost 决定是否打出，再看节点图决定效果），故表单应**永远可见**。

```
┌─────────────────────────────────────────────────────────┐
│ [Name] [Cost 1] [Type Attack] [Rarity Common] [Keywords] │  ← 表单 (40-50px)
├─────────────────────────────────────────────────────────┤
│                          │                              │
│     节点画布 (居中)        │   [生成代码 ▼] 预览 textarea   │  ← 主区域
│     toolbar              │   (默认折叠, 点开 200px)       │
│                          │                              │
└─────────────────────────────────────────────────────────┘
```

布局原则:
- **顶部表单横排**：6 字段横排, name 与 cost 同级, type/rarity 下拉, keywords 是 chip input (逗号分隔); description 单独行 (textarea, 折叠时只露 1 行)
- **主区域二分**：节点画布 (2/3 宽) + 折叠预览 (1/3 宽, 默认收起)
- **工具栏融入画布上方**：跟 RelicEditor 一样 — undo/redo + 添加 trigger/effect 按钮 + 生成代码按钮
- **预览默认折叠**：点 [生成代码 ▼] 展开 textarea; 错误时自动展开高亮

与 RelicEditor 的差异: 不再是三段并列 (左表单/中节点/右预览), 而是顶部表单 + 主体节点 + 右侧折叠预览. 形态不同因为 Card 字段多 + 节点图通常比 Relic 简单 (单 trigger + 1-3 effect).

### 8. 形态 2 effect 节点 data 结构 + codegen target 字段

#### 8.1 data 字段极简
形态 2 effect (`applyBuffToEventTarget` / `applyDebuffToEventTarget`) 的 data 字段极简 — 只 `{ buff: string, stacks: number }`. 真实 mod 99% 是 "any card" 触发, 不需要 cardTypeFilter / rarityFilter. 筛选需求留给 v0.10+ 的 condition 节点.

#### 8.2 effect 节点加 `target` 字段（灵活 codegen）

虽然 Q5 走法 2 锁定"实体绑定 effect 各占一条", 但**每个 effect 节点的 data 还可携带 target 选项**, 让 codegen 决定 prefix:

```ts
applyBuff: {
  defaultData: { 
    buff: '', 
    stacks: 1, 
    target: 'self',  // 'self' | 'eventTarget' | 'exhaustedCard' | 'discardedCard'
  },
},
```

codegen 看到 `target: 'eventTarget'` 时, emit `card.ApplyBuff(...)` (eventTarget 是 trigger 参数 placeholder).
看到 `target: 'self'` 时, emit `ApplyBuff(...)` (默认).

这条规则的实用场景: 同一个 `applyBuff` effect, 既能在 `onAnyCardExhausted` 后 (codegen 用 `card.ApplyBuff`) 也能在 `onCombatStart` 后 (codegen 用 `ApplyBuff`)。命名 (`applyBuffToEventTarget`) 是"默认 target 的语法糖", data.target 是"用户主动覆盖 target"。

#### 8.3 validateGraph 新规则: 形态 2 effect 不在形态 2 trigger 后拒绝

```ts
function validateGraph(graph: NodeGraph): Result {
  // 找所有 trigger 节点
  const triggers = graph.nodes.filter(n => n.type === 'trigger')
  
  // 分类
  const anyTriggers = triggers.filter(n => n.data.kind.startsWith('onAny'))
  const normalTriggers = triggers.filter(n => !n.data.kind.startsWith('onAny'))
  
  // BFS 从普通 trigger 出发, 收集 effect.kind
  const effectsFromNormal = bfsCollect(normalTriggers)
  for (const effect of effectsFromNormal) {
    if (effect.data.kind.endsWith('ToEventTarget') || effect.data.kind.endsWith('Card')) {
      return { ok: false, reason: `Effect '${effect.data.kind}' must follow an Any trigger (onAny*)` }
    }
  }
  
  // BFS 从 Any trigger 出发, 收集 effect.kind — 任何 effect 都允许
  // (通用 effect 操作 self, 形态 2 effect 操作 eventTarget)
}
```

这条规则跟 §决策 §4 的 trigger.entity 规则**叠加**:
- 规则 1: trigger.entity === graph.entityType (跨实体 trigger 拒绝)
- 规则 2 (新): 形态 2 effect 不在形态 2 trigger 后拒绝

#### 8.4 codegen target 字段优先级

```ts
function renderEffectNode(node: GraphNode, triggerKind: string): string {
  const kindDef = EFFECT_KINDS[node.data.kind]
  
  // 1. data.target 优先 (用户显式覆盖)
  if (node.data.target && node.data.target !== 'self') {
    const prefix = triggerKindToEventArg(triggerKind) // 'card' / 'discardedCard' / ...
    return `${prefix}.${kindDef.methodName}(${formatArgs(node.data)})`
  }
  
  // 2. 形态 2 effect 默认 = eventTarget (命名约定)
  if (node.data.kind.endsWith('ToEventTarget') || node.data.kind.endsWith('Card')) {
    const prefix = triggerKindToEventArg(triggerKind)
    return `${prefix}.${kindDef.methodName}(${formatArgs(node.data)})`
  }
  
  // 3. 通用 effect 默认 = self (this / 当前 Relic)
  return `${kindDef.methodName}(${formatArgs(node.data)})`
}

function triggerKindToEventArg(triggerKind: string): string {
  if (triggerKind === 'onAnyCardExhausted') return 'card'
  if (triggerKind === 'onAnyCardDiscarded') return 'card'
  // v0.10+ 加 onAnyEnemyDeath 等时, 这里扩展
  throw new Error(`Unknown Any trigger: ${triggerKind}`)
}
```

#### 8.5 形态 2 effect 的 UI label 区分

避免用户混淆通用 effect 与形态 2 effect, UI 层 label 显式区分:
- `applyBuff`: "附加 buff (自身)"
- `applyBuffToEventTarget`: "附加 buff (事件目标)"

## 备选方案（Alternatives Considered）

### 备选 A：Card 不接入节点图（v0.9 跳过）

- **理由**：Card 表单 + AI 生成已经覆盖 90% 真实用例，节点图 ROI 低
- **拒绝原因**：
  - "卡自触发"（形态 1）的复合卡真实存在（升级版 Bash 类、消耗触发类）
  - 评审候选 5（kinds registry 注入 validateGraph）的真正价值是 AI 输出节点图 — Card 不接入 = AI JSON Schema 失去最大载体
  - 跳过 Card 意味着 v0.9 仍要做 E5/E6 实体，它们与 Relic 完全同构，无新决策价值

### 备选 B：部分同构（只有 effect，无 trigger）

- **理由**：Card 触发统一 `OnPlay`，省去 trigger 节点；UI 更简单
- **拒绝原因**：
  - 失去"条件触发"表达力（onSelfDraw / onSelfExhaust 类卡无法表达）
  - 与 Relic 模型不同构 → codegen 不能共用 `collectStatements`（要写两份 BFS 逻辑）
  - 未来 v0.10+ 加 Potion / Enemy 时会重复同一纠结

### 备选 C：TRIGGER 表分表（relic/kinds.ts vs card/kinds.ts）

- **理由**：每个实体自治，文件隔离
- **拒绝原因**：
  - 加新实体时改 N 个文件（v0.10 加 Enemy 又新建 `enemy/kinds.ts`）
  - 共享 trigger（如 `onTurnEnd` 既能在 Relic 又能在 Enemy 用）要在 N 张表复制
  - "过早拆分"陷阱 — v0.9 阶段只有两个实体，看不出共享 trigger 需求

### 备选 D：形态 1 / 形态 2 不区分命名

- **理由**：`onExhaust` 既能表"卡自触发"又能表"全局监听"，靠 codegen 上下文推断
- **拒绝原因**：
  - C# 方法签名不同（Self 收 `this`，Any 收 `exhaustedCard` 参数），命名应显式
  - 不区分 → validateGraph 没法拒绝"Card 节点图里塞 onAnyCardExhausted"

### 备选 E：Card trigger 表只保留 onPlay（最极简）

- **理由**：onPlay 覆盖 95% 卡，onSelfDraw 真实但低频，onSelfExhaust / onSelfDiscard 几乎不用
- **拒绝原因**：
  - 用户（grill 评审）明确表示**两种形态都要**——"卡自触发 + 全局监听都有真实用例"
  - 砍掉 onSelfExhaust / onSelfDiscard 等于放弃形态 1 的复合卡（升级版 Bash / 消耗触发类）

### 备选 F：EFFECT_KINDS 全部共享 + target 字段（走法 1）

- **理由**：单表最简，所有 effect 都用同一条 schema，`target` 字段决定 codegen 时谁接收
- **拒绝原因**：
  - `dealDamage` 的 target 有 `enemy/self/allEnemies/anyEnemy/eventTarget/randomEnemy` 6 种 — target 字段膨胀
  - 命名（`exhaustSelf` vs `exhaustCard`）比 target 推断更清晰
  - codegen 看到 `exhaustCard` 直接调 `ExhaustCard(targetCard)`，看到 `exhaustSelf` 直接调 `ExhaustSelf()` — 不用看 target 字段

### 备选 G：EFFECT_KINDS + forms 数组（走法 3）

- **理由**：forms 数组显式标记 effect 适用哪些实体 + 形态
- **拒绝原因**：
  - 大部分 effect 是全 forms，标 forms 数组等于无信息
  - 增加 `validateGraph` 检查负担（forms 匹配 entityType），但实际语义由 UI 守门更合适

### 备选 H：形态 2 effect data 不加 target 字段 (纯命名约定)

- **理由**：命名 (`applyBuffToEventTarget`) 已经携带 target 语义, codegen 看 kind 即可
- **拒绝原因**：
  - 不灵活: 同一 effect kind 在不同 trigger 后的 target 应该可选 — 比如 `applyBuff` 在 `onAnyCardExhausted` 后用户**可能**想要"给被消耗的卡加 buff" 而不是"自身加 buff"
  - 加 `target` 字段让用户**显式选择**而不是被命名绑死
  - Q7-3 评审明确选 target 字段方案

### 备选 I：validateGraph 不加形态 2 effect 规则

- **理由**：靠 UI palette 过滤 + codegen 报错足够
- **拒绝原因**：
  - JSON 导入路径绕过 UI 过滤, 损坏数据可被持久化
  - validateGraph 是**所有路径共用的契约校验**, 应包含完整规则
  - Q7-2 评审明确选加规则

## 关键发现

### 形态 1 vs 形态 2 不是 trigger 表的范围问题，是命名问题

grill 过程发现：用户说的"onDiscard / onExhaust 用例"实际上**两种形态都要**：
- 形态 1（卡自触发）：卡 X 自己被消耗时触发效果
- 形态 2（全局监听）：装备的 Relic 监听任意卡被消耗

如果不区分命名 → validateGraph 不知道 Card 节点图里能不能放形态 2 的 trigger → 跨实体污染。

加 `Self` / `Any` 前缀后 → 方法名携带语义 → C# 签名明确（Self 收 `this`、Any 收事件参数） → codegen 可机械翻译 → validateGraph 可机械校验。

### EFFECT_KINDS 100% 共享的边界

`dealDamage / healHp / applyBuff / gainBlock` 这些 effect 是**通用副作用** — 不属于 Card 或 Relic 特有。卡打出时"对敌人造成 6 点伤害"与遗物"装备后每回合对敌人造成 6 点伤害"是**同一个 effect**，只是触发器不同。

**但**：`exhaustSelf` / `exhaustCard` / `applyBuffToEventTarget` 等**实体绑定 effect** 不共享 — C# 方法签名不同（Self 收 `this`，Card 收 `targetCard` 参数），命名应显式区分。

这条原则同样适用于 v0.10+ 的 Potion / Enemy / Event：通用 effect 在 EFFECT_KINDS 大表里，实体绑定 effect 各占一条。

只有 trigger 是**实体绑定**的（每个实体有自己的事件时点），effect 是**通用副作用 + 实体绑定 effect 各占一条**的混合。

### EFFECT_KINDS 拆分 vs trigger 拆分的非对称

- **trigger**：完全靠 `entity` 字段分组（Card / Relic / Enemy / Event 各自的范围不重叠）
- **effect**：混合形态 — 通用副作用共享 + 实体绑定 effect 各占一条

非对称的原因：trigger 的"事件时点"是**每个实体独有的事实**（Card 没有 onCombatStart，Relic 没有 onPlay），effect 的"动作"是**通用副作用**加上**实体特异动作**（dealDamage 通用，但 exhaustSelf 是 Card 特有）。

### validateGraph 规则的扩展时机

v0.9 之前 `validateGraph` 不检查 trigger.entity，因为 Relic 是唯一实体类型，无跨实体需求。v0.9 加 Card 后，**第一次出现跨实体可能性**，必须加这条规则。

推后加 = v0.9 上线后发现"CardEditor 误显示 onCombatStart"再补 — 成本远高于一开始就有。

### effect 与 trigger 的 `entity` 字段非对称处理

- **trigger 的 entity 字段**：validateGraph 强校验（Card 节点图里出现 onCombatStart → 拒绝）
- **effect 的 entity 字段**：validateGraph **不校验**（Card 节点图里出现 applyBuffToEventTarget → 不拒绝，但 codegen 时报"形态 2 effect 不在形态 2 trigger 后"）

理由：trigger 的跨实体是**用户错误**（拖错节点），effect 的跨实体是**潜在设计**（Card 节点图里 applyBuffToEventTarget 可能是新形态的预告）。UI 层 palette 按 entity 过滤更友好。

## 后果（Consequences）

### 正面

- **代码量净减**：Card 不需要独立 BFS / 独立 trigger 表 / 独立 validateGraph 规则集 — 共用层（`useNodeGraph` / `collectStatements` / `EFFECT_KINDS`）增加 ~10%，但 v0.10+ 加 Potion / Enemy 时几乎零增量。
- **AI JSON Schema 落地**（评审候选 5）：Card 节点图是 AI 输出的最大载体 — 提示词可写"为这张卡设计一个 trigger→effect 链"，AI 输出 JSON 走 `validateGraph` → `collectStatements` → `generateCardCode`。
- **codegen 测试可重用**：Card 的 codegen 测试可以借用 Relic 的 BFS 测试用例（只换 trigger 名称 + effect data）。
- **跨实体 trigger 不可能误用**：`Self` / `Any` 前缀让"Card 节点图里塞 onAnyCardExhausted"被 validateGraph 当场拒绝。
- **effect 命名即语义**：`exhaustSelf` ↔ `ExhaustSelf()` / `exhaustCard` ↔ `ExhaustCard(targetCard)`，codegen 机械翻译不用 target 推断。

### 负面

- **Card 表单 + 节点图并存**：CardEditor 同时有表单（name / cost / type / description）和节点画布。UI 层需要 tab 切换或上下分区 — CardEditor.tsx 文件会比 RelicEditor 复杂。
- **trigger 列表不再对称**：Card 4 个（onPlay / onSelfDraw / onSelfExhaust / onSelfDiscard），Relic 7 个（含 2 个 Any 全局监听）。不是"两边都对齐" — 但这是真实需求差异，不应人为对齐。
- **`onAnyCardExhausted` 的 C# 签名复杂**：要传 `exhaustedCard` 参数进 `OnAnyCardExhausted(MyCardComponent card)`。codegen 渲染 effect 节点时，要从 effect.data 读 "对被消耗的卡做什么"，不是简单的 `DealDamage(6)`。这是 v0.9 codegen 唯一新增的复杂度。

### 中性

- **entity 字段是单值还是数组**：当前是单值（`'card' | 'relic' | 'enemy' | 'event'`）。如果将来出现"Relic 与 Enemy 共享 trigger"（如 `onDeath`），改为数组即可 — 这是 v0.10+ 决策，v0.9 阶段保持单值。

## 验证（Validation）

- [ ] v0.9 实施后：`useNodeGraph('card-1', 'card')` 与 `useNodeGraph('relic-1', 'relic')` 接口完全一致
- [ ] `validateGraph` 拒绝 `entityType='card'` 的图里出现 `onCombatStart` 节点
- [ ] `collectStatements` 在 Card 和 Relic 上输出格式一致（只有 trigger.methodName 不同）
- [ ] AI 生成 Card 节点图：JSON Schema 与 Relic 节点图同构（共享 `node.type` + `node.data.kind`）
- [ ] `EffectKind` 测试用例 100% 复用（dealDamage / gainBlock 等不重写）

# ADR-0006：v0.9 Card 节点 schema — 单一 Card 模型与线性 trigger→effect 链

> 状态：已接受 · 日期：2026-08-12 · 修订：2026-08-13 · 来源：`/grill-with-docs` 评审（2026-08-12、2026-08-13）
> 适用范围：v0.9 “卡牌接入节点编辑器”的端到端形态；Relic Any/EventTarget 仅保留为 v0.10 设计方向

## 背景（Context）

v0.8 完成架构清理（评审 5 候选 3/5 ✅）后，v0.9 起点评估指向 **E1 卡牌接入节点图**。现有节点编辑器（`useNodeGraph` + `kinds.ts` + `RelicEditor.codegen`）是事件驱动模型（trigger→effect 链），与卡牌的语义形态是否同构需要先敲定。

v0.7 / v0.8 时 Card 仍为纯表单 + 实时预览；Codegen 是文本字段级（`generateCardCode` 用 Mustache 渲染）。问题：

1. **是否复用 trigger→effect 模型** — Card 与 Relic 是不是同一种"事件驱动实体"？
2. **trigger 表怎么拆分** — 大表 / 分表 / 共享？
3. **trigger 列表范围** — Card 真需要哪些 trigger？
4. **"卡自触发" vs "全局监听"** — `onDiscard` / `onExhaust` 两种语义形态要不要都在 Card 表里？

## 决策（Decision）

### 1. 完全同构 trigger→effect 链

Card 复用 Relic 的节点图模型：

- 一个 Card 草稿可包含 0..N 个 trigger 根；可生成 Card 必须包含 1..N 个 trigger 根，每个完整分支至少有一个 effect
- 同一种 trigger 在一张 Card 中最多出现一次；重复 trigger 会生成重复 override 方法，因此生成校验必须拒绝
- 每个 trigger 可连接 0..N 个 effect，以表达一张 Card 的多个不同触发时机
- 每个 effect 必须只从一个 trigger 根可达；多个 trigger 不得汇入并共享同一个 effect 节点
- 不同触发分支需要相同行为时复制 effect 节点；显式“可复用动作组”不属于 v0.9 范围
- v0.9 中每个触发分支是线性效果链：trigger/effect 的 flow output 最多一条出边，每个 effect input 最多一条入边
- 效果链的连线顺序就是代码执行顺序；不得依赖 `edges[]` 插入顺序或画布坐标推断语义
- condition/branch 真正进入产品范围时，再以显式分支语义扩展；v0.9 不预先支持 effect 分叉
- `useNodeGraph(cardId, 'card', initial?)` 与 `useNodeGraph(relicId, 'relic', ...)` 同形
- codegen 复用确定性的线性链遍历逻辑，共用 `EFFECT_KINDS` 表
- 模板差异：Card 模板 `cardTemplate.mustache`，Relic 模板 `relicTemplate.mustache`

### 2. TRIGGER_KINDS 大表 + `entity` 字段（A1）

`src/node-editor/kinds.ts`（或新建 `src/shared/kinds.ts`）维护**一张大表**，每条 trigger 定义加 `entity: 'card' | 'relic' | 'enemy' | 'event'` 字段：

```ts
export const TRIGGER_KINDS = {
  // Card 形态 1（卡自触发）
  onPlay:           { entity: 'card',  label: '使用卡牌',     methodName: 'OnPlay' },
  onSelfDraw:       { entity: 'card',  label: '抽到自身',     methodName: 'OnSelfDraw' },
  onSelfExhaust:    { entity: 'card',  label: '自身被消耗',   methodName: 'OnSelfExhaust' },
  onSelfDiscard:    { entity: 'card',  label: '自身被弃',     methodName: 'OnSelfDiscard' },
  // Relic 已有（v0.5.2 起）
  onCombatStart:    { entity: 'relic', label: '战斗开始',     methodName: 'OnCombatStart' },
  onCombatEnd:      { entity: 'relic', label: '战斗结束',     methodName: 'OnCombatEnd' },
  onTurnStart:      { entity: 'relic', label: '回合开始',     methodName: 'OnTurnStart' },
  onTurnEnd:        { entity: 'relic', label: '回合结束',     methodName: 'OnTurnEnd' },
  // Relic v0.10 方向（v0.9 不注册）
  onAnyCardExhausted:  { entity: 'relic', label: '任意卡被消耗', methodName: 'OnAnyCardExhausted' },
  onAnyCardDiscarded:  { entity: 'relic', label: '任意卡被弃',   methodName: 'OnAnyCardDiscarded' },
} as const
```

UI 层（`NodeGraphCanvas` 工具栏 + `useNodeGraph.addNode`）按 `entity` 字段过滤：CardEditor 看不到 Relic trigger，反之亦然。

### 3. Self / Any 前缀命名约定（关键）

**Self 前缀 = 形态 1（卡自触发）**：`onSelfDraw` / `onSelfExhaust` / `onSelfDiscard` — 触发器绑定到**这张卡自己**的行为。

**Any 前缀 = 形态 2（全局监听）**：`onAnyCardExhausted` / `onAnyCardDiscarded` — 监听器订阅**任意卡**的事件，由装备它的实体（Relic）响应。

无前缀（`onPlay` / `onCombatStart` / `onTurnEnd`）= 默认形态（按上下文自明）。

这个命名约定的语义价值：codegen 看方法名就知"有没有事件参数" — `OnSelfExhaust` 收 `this`，`OnAnyCardExhausted` 收 `exhaustedCard` 参数。

### 4. validateGraph 新规则

`validateGraph` v0.9 起加一条规则：

```ts
// trigger 的 entity 字段必须匹配 graph 的 entityType
if (node.type === 'trigger' && triggerDef.entity !== graph.entityType) {
  return { ok: false, reason: `Trigger '${kind}' 不允许用于实体类型 '${entityType}'` }
}
```

避免"CardEditor 里不小心拖入了 `onCombatStart` Relic trigger"这类跨实体污染。

### 5. codegen 复用粒度

`collectStatements(graph: NodeGraph, triggerId: string): string[]` **完全共用**（从 trigger.out 沿唯一后继顺序遍历 effect 节点，渲染 C# 语句）。

模板层差异（`cardTemplate.mustache` vs `relicTemplate.mustache`）由 `generateCardCode` / `generateRelicCode` 各自包装。

### 6. EFFECT_KINDS 大表 + 目标化 effect kind

**目标与上下文完全相同的副作用**可以共享 — 例如 Card.OnPlay 和 Relic.OnCombatStart 的 `drawCards` 都让玩家抽牌，EFFECT_KINDS 只需一个条目。

**动作接收者不同的 effect**各占一条：
- Card 专属：`exhaustSelf` / `discardSelf` / `addCardToHand` / `addCardToDeck`（命名带 `Self` 后缀，C# 方法是 `ExhaustSelf()` 等）
- v0.10 形态 2 专属：`exhaustEventTarget` / `applyBuffToEventTarget` / `applyDebuffToEventTarget`（命名带 `EventTarget` 后缀，C# 方法使用 trigger 提供的事件参数）
- 其他存在目标差异的动作同样在 kind 中区分，例如 v0.9 的 `applyBuffToOwner` 与 v0.10 才会注册的 `applyBuffToEventTarget`

核心约束：kind 是动作与接收者的唯一序列化表示。节点实例不得携带通用 `data.target` 覆盖 kind 语义；注册定义可用静态 `receiver` 元数据帮助校验和 codegen，但该值由 kind 固定。

接收者使用统一词汇：`Self` 是当前拥有行为图的实体；`Owner` 是持有该实体的玩家或角色；`EventTarget` 是 Any trigger 提供的事件参数。名称不得让 `Self` 在实体与 Owner 之间随上下文改变含义。

```ts
export const EFFECT_KINDS = {
  // 目标明确且可共享
  dealDamageToRandomEnemy: { label: '对随机敌人造成伤害', receiver: 'randomEnemy', defaultData: { amount: 0 } },
  applyBuffToOwner:        { label: '给持有者附加 buff', receiver: 'owner', defaultData: { buff: '', stacks: 1 } },
  drawCards:   { label: '抽牌',        defaultData: { amount: 1 } },
  gainEnergy:  { label: '获得能量',    defaultData: { amount: 1 } },
  // Card 专属（Self 后缀）
  exhaustSelf:    { entity: 'card',  label: '消耗自身',  defaultData: {} },
  discardSelf:    { entity: 'card',  label: '弃掉自身',  defaultData: {} },
  addCardToHand:  { entity: 'card',  label: '向手牌加牌', defaultData: { kind: '', amount: 1 } },
  addCardToDeck:  { entity: 'card',  label: '向牌堆加牌', defaultData: { kind: '', amount: 1 } },
  // Relic EventTarget kinds 留待 v0.10 验证后再注册。
} as const
```

所有输入路径都必须校验 effect 是否已注册、其 `entity` 是否适用于当前实体、其固定 `receiver` 是否能由当前 trigger 上下文满足。UI palette 的过滤只是交互便利，不是数据安全边界。v0.9 未注册的 EventTarget effect 作为未知 kind 进入保真只读恢复；v0.10 注册后再启用其事件上下文规则。

### 7. CardEditor UI 布局 — 走法 1（顶部表单横排 + 下部节点图 + 折叠预览）

Card 表单字段比 Relic 多（6 个 vs 5 个），且 cost/type/rarity/keywords 是**核心身份字段**（玩家先看 cost 决定是否打出，再看节点图决定效果），故表单应**永远可见**。

```
┌─────────────────────────────────────────────────────────┐
│ [Name] [Cost 1] [Type Attack] [Rarity Common] [Keywords] │  ← 表单 (40-50px)
├─────────────────────────────────────────────────────────┤
│                          │                              │
│     节点画布 (居中)        │   [生成代码 ▼] 预览 textarea   │  ← 主区域
│     toolbar              │   (默认折叠, 点开 200px)       │
│                          │                              │
└─────────────────────────────────────────────────────────┘
```

布局原则:
- **顶部表单横排**：6 字段横排, name 与 cost 同级, type/rarity 下拉, keywords 是 chip input (逗号分隔); description 单独行 (textarea, 折叠时只露 1 行)
- **主区域二分**：节点画布 (2/3 宽) + 折叠预览 (1/3 宽, 默认收起)
- **工具栏融入画布上方**：跟 RelicEditor 一样 — undo/redo + 添加 trigger/effect 按钮 + 生成代码按钮
- **预览默认折叠**：点 [生成代码 ▼] 展开 textarea; 错误时自动展开高亮

与 RelicEditor 的差异: 不再是三段并列 (左表单/中节点/右预览), 而是顶部表单 + 主体节点 + 右侧折叠预览. 形态不同因为 Card 字段多 + 节点图通常比 Relic 简单 (单 trigger + 1-3 effect).

### 8. v0.10 方向：形态 2 effect 节点 data 结构 + 目标化 kind

本节保留已经明确的 Any/EventTarget 语义，但不属于 v0.9 交付范围。v0.9 不注册 `onAnyCard*` trigger 或 EventTarget effect，不接受包含这些 kind 的新 Card/Relic JSON，也不生成相关 C#。实现前需在 v0.10 重新核对游戏运行时 API。

#### 8.1 data 字段极简
形态 2 effect (`applyBuffToEventTarget` / `applyDebuffToEventTarget`) 的 data 字段极简 — 只 `{ buff: string, stacks: number }`. 真实 mod 99% 是 "any card" 触发, 不需要 cardTypeFilter / rarityFilter. 筛选需求留给 v0.10+ 的 condition 节点.

#### 8.2 effect 目标只有一种序列化方式

节点实例只保存 kind 自身需要的参数。例如 `applyBuffToEventTarget` 只保存 `{ kind, buff, stacks }`，不保存 `target`。要把 buff 施加给持有者，使用另一个明确的 kind（例如 `applyBuffToOwner`）。因此不存在 `{ kind: 'applyBuffToEventTarget', target: 'owner' }` 这类冲突状态。

#### 8.3 validateGraph 新规则: 形态 2 effect 不在形态 2 trigger 后拒绝

```ts
function validateGraph(graph: NodeGraph): Result {
  // 找所有 trigger 节点
  const triggers = graph.nodes.filter(n => n.type === 'trigger')
  
  // 分类
  const anyTriggers = triggers.filter(n => n.data.kind.startsWith('onAny'))
  const normalTriggers = triggers.filter(n => !n.data.kind.startsWith('onAny'))
  
  // BFS 从普通 trigger 出发, 收集 effect.kind
  const effectsFromNormal = bfsCollect(normalTriggers)
  for (const effect of effectsFromNormal) {
    if (EFFECT_KINDS[effect.data.kind].receiver === 'eventTarget') {
      return { ok: false, reason: `Effect '${effect.data.kind}' must follow an Any trigger (onAny*)` }
    }
  }
  
  // BFS 从 Any trigger 出发, 收集 effect.kind — 任何 effect 都允许
  // (通用 effect 操作 self, 形态 2 effect 操作 eventTarget)
}
```

这条规则跟 §决策 §4 的 trigger.entity 规则**叠加**:
- 规则 1: trigger.entity === graph.entityType (跨实体 trigger 拒绝)
- 规则 2 (新): 形态 2 effect 不在形态 2 trigger 后拒绝

#### 8.4 codegen 从 kind 定义读取 receiver

```ts
function renderEffectNode(node: GraphNode, triggerKind: string): string {
  const kindDef = EFFECT_KINDS[node.data.kind]

  if (kindDef.receiver === 'eventTarget') {
    const prefix = triggerKindToEventArg(triggerKind)
    return `${prefix}.${kindDef.methodName}(${formatArgs(node.data)})`
  }

  return `${kindDef.methodName}(${formatArgs(node.data)})`
}

function triggerKindToEventArg(triggerKind: string): string {
  if (triggerKind === 'onAnyCardExhausted') return 'card'
  if (triggerKind === 'onAnyCardDiscarded') return 'card'
  // v0.10+ 加 onAnyEnemyDeath 等时, 这里扩展
  throw new Error(`Unknown Any trigger: ${triggerKind}`)
}
```

#### 8.5 形态 2 effect 的 UI label 区分

避免用户混淆通用 effect 与形态 2 effect, UI 层 label 显式区分:
- `applyBuffToOwner`: "附加 buff (持有者)"
- `applyBuffToEventTarget`: "附加 buff (事件目标)"

### 9. 原位升级现有 Card 编辑流程，保持单一 Card 模型

v0.9 在现有 Card 编辑流程中加入行为图，不创建并行的“节点版 Card”子系统。卡牌基本属性与 `NodeGraph` 共同描述同一张卡；现有卡牌列表、选择、校验、AI 输入输出、项目加载与保存路径继续服务同一个 Card 模型。

因此：

- Card 只有一份权威数据模型；节点编辑能力不得复制 Card 类型、Store、编辑器入口或文件读写链路。
- effect 目标由目标化 kind 唯一表达，不属于 Card 全局属性，也不得由节点级通用 `target` 字段覆盖。
- v0.9 的编辑器改造必须保留现有卡牌管理能力，而不是以一个脱离项目与 Store 的新编辑器替代它。

### 10. Card ID 是不可变的稳定身份

Card 首次落盘前由用户确认 `id`，之后不可直接编辑。ID 是以英文字母开头、只含 ASCII 英文字母和数字的 PascalCase 代码标识符，并在项目内按不区分大小写比较唯一；冲突必须明确报告，不静默追加后缀。若显示名称无法可靠生成 ID，创建流程要求用户输入或确认。

`name` 只表示玩家可见名称；重命名不得改变行为图关联、C# 类名或文件名。行为图关联、Store 的选择/更新/删除，以及 Card 文档、C# 类名和生成文件名均以 Card ID 为准；数组索引只表达当前显示顺序。

既有 Card 首次进入新模型时，从已生成的类名或文件名迁移出唯一 Card ID。迁移检测到重复 ID 时必须报告冲突，不得静默覆盖。

Card 及行为图的权威数据来自 `.modstudio/`；`scripts/Cards/*.cs` 只是可重新生成的产物。C# 反向解析仅用于尚无 `.modstudio/` 数据的旧项目完成一次性迁移，详见 ADR-0003。

每张 Card 的基本属性与行为图保存在同一份 Card 文档中，形成保存和 schema 迁移的原子边界；`entities.json` 只作可重建索引，详见 ADR-0003。

Card 使用两级校验：结构校验通过即可把半成品保存为 Card 草稿；生成校验要求至少一个 trigger、同类 trigger 唯一、每个 trigger 至少连接一个 effect、无孤立节点、参数齐全、效果链及 effect receiver 上下文合法。只有生成校验通过才更新 C#。生成校验或产物写入失败时保留项目源数据与上一次成功生成的 C#，不回滚用户编辑，详见 ADR-0003。

空 trigger 可以作为编辑中的草稿保存，但显式生成时必须拒绝并定位到该 trigger；不得生成空 override，也不得静默忽略该分支。

表单或行为图变化后防抖自动保存 Card 文档，并在切换 Card、切换项目或关闭窗口前强制 flush。C# 生成必须由用户显式触发；自动保存不更新生成产物。UI 独立显示草稿保存状态与生成产物状态。

Card 表单修改与行为图 mutation 进入同一条 Card 级撤销时间线，快照边界是完整 Card 草稿。自动保存和 C# 生成不进入历史；每张 Card 独立维护历史，详见 ADR-0005。

历史按编辑事务分步：同字段连续输入以约 750ms 停顿或失焦收束，一次节点拖动从按下到释放只算一步，下拉选择、关键词增删、节点/边增删等离散操作各自成步。事务合并由历史层统一处理，详见 ADR-0005。

AI 修改先形成通过结构校验的完整 Card 提案，预览属性与图变化；用户确认后才作为一个编辑事务应用到当前草稿，因此一次撤销可整体恢复。应用后允许自动保存草稿，但不自动生成 C#，详见 ADR-0002。

AI 提案绑定请求时的 Card revision。响应返回时若当前草稿已变化，提案标记过期，只可查看且必须基于最新草稿重新生成；v0.9 不锁定编辑器、不强制覆盖，也不自动三方合并图，详见 ADR-0002。

旧项目一次性导入时创建空行为图的迁移草稿，只恢复能够从旧 C# 证明的 Card ID 和基本属性；不自动添加 `onPlay`，也不尝试从任意方法体部分推导节点。用户完成行为图前保留旧 C# 不变，详见 ADR-0003。

删除 Card 默认移入项目内回收站：Card 文档和当前生成产物都离开活动目录，因此游戏不再加载它；恢复时重新检查 Card ID 冲突。永久删除是单独的显式操作，详见 ADR-0003。

删除必须具有原子用户语义：先完整暂存回收站，再移除活动文件；只有确认活动 C# 不存在后才从 UI 移除 Card。失败时补偿恢复并保持 Card 活跃，详见 ADR-0003。

Card 文档包含未知 trigger/effect kind 或未来 schemaVersion 时，以保真只读模式隔离该 Card：保留原始数据，只允许查看和导出，禁止编辑、自动保存及生成；其他 Card 不受影响，详见 ADR-0003。

已知旧版 schema 通过逐版本纯函数链迁移。首次写回前备份原文档，当前结构校验通过后原子替换；失败只让该 Card 进入保真只读恢复，不阻塞项目，详见 ADR-0003。

Card 文档记录最近成功生成的“生成指纹”：生成语义哈希只覆盖会改变 C# 的规范化 Card 字段、kind、effect 参数与效果链顺序，排除节点坐标和时间戳；生成器版本覆盖模板、kind emit 与 codegen 行为；产物哈希来自写盘后重新读取的实际 C#。三者共同判断同步与外部修改状态，因此重启和生成器升级后仍可恢复，详见 ADR-0003。

磁盘 C# 的 artifactHash 与记录不一致时，视为外部修改：阻止测试与无提示覆盖。用户可以先备份或导出外部版本再重新生成，但不得把 C# 反向合并进 Card 文档。

项目级批量生成逐 Card 独立执行：草稿与保真只读 Card 作为“跳过”，单张失败不阻塞其他可生成 Card，每张成功后独立更新生成指纹，最后输出成功/跳过/失败报告，详见 ADR-0003。

启动游戏前执行测试预检：未生成过 C# 的草稿可明确排除；会被加载但缺失、写入失败或生成器过期的产物阻止启动；当前草稿比现有 C# 新时默认阻止，但用户可为本次启动明确选择测试上次生成版本。预检不自动生成，详见 ADR-0003。

### 11. v0.9 发布范围只包含 Card 端到端

v0.9 交付单一 Card 模型、Card 文档持久化与迁移、统一历史、AI 提案、4 个 Card trigger、Card 可用的 Self/Owner effect、代码生成、同步判定与测试预检。Relic 的 `onAnyCard* → EventTarget effect` 完整链路延后到 v0.10。

共享 kind registry 可先支持静态 receiver 元数据，但不得在 v0.9 注册或向 UI/AI schema 暴露尚未经过运行时 API、codegen 和集成测试验证的 Relic Any/EventTarget kind。

### 12. 内部小步实施，用户侧一次切换

v0.9 在开发过程中按可验证的纵向切片小步提交，每一步保持现有测试与新增测试全绿；对用户则在完整 Card 端到端链路就绪后一次发布。实施期间不得保留第二套 CardData、平行 CardEditor 或长期功能开关。

具体依赖顺序与逐提交验收见 [v0.9 Card 节点编辑器实施计划](../v0.9-card-node-editor-implementation-plan.md)。

建议切片顺序：

1. 单一 Card 模型、不可变 Card ID 与 Card 文档 schema/迁移。
2. Card 级统一历史与原位 CardEditor 接入行为图。
3. Card trigger/effect registry、线性效果链与两级校验。
4. 显式 codegen、生成指纹、artifactHash 与外部修改保护。
5. 草稿自动保存、删除/恢复、批量生成与测试预检。
6. AI 完整提案、revision 过期检测与最终端到端验收。

每个切片完成后删除已经被替代的旧路径，不让双轨数据模型跨切片累积。

## 备选方案（Alternatives Considered）

### 备选 A：Card 不接入节点图（v0.9 跳过）

- **理由**：Card 表单 + AI 生成已经覆盖 90% 真实用例，节点图 ROI 低
- **拒绝原因**：
  - "卡自触发"（形态 1）的复合卡真实存在（升级版 Bash 类、消耗触发类）
  - 评审候选 5（kinds registry 注入 validateGraph）的真正价值是 AI 输出节点图 — Card 不接入 = AI JSON Schema 失去最大载体
  - 跳过 Card 意味着 v0.9 仍要做 E5/E6 实体，它们与 Relic 完全同构，无新决策价值

### 备选 B：部分同构（只有 effect，无 trigger）

- **理由**：Card 触发统一 `OnPlay`，省去 trigger 节点；UI 更简单
- **拒绝原因**：
  - 失去"条件触发"表达力（onSelfDraw / onSelfExhaust 类卡无法表达）
  - 与 Relic 模型不同构 → codegen 不能共用 `collectStatements`（要写两份 BFS 逻辑）
  - 未来 v0.10+ 加 Potion / Enemy 时会重复同一纠结

### 备选 C：TRIGGER 表分表（relic/kinds.ts vs card/kinds.ts）

- **理由**：每个实体自治，文件隔离
- **拒绝原因**：
  - 加新实体时改 N 个文件（v0.10 加 Enemy 又新建 `enemy/kinds.ts`）
  - 共享 trigger（如 `onTurnEnd` 既能在 Relic 又能在 Enemy 用）要在 N 张表复制
  - "过早拆分"陷阱 — v0.9 阶段只有两个实体，看不出共享 trigger 需求

### 备选 D：形态 1 / 形态 2 不区分命名

- **理由**：`onExhaust` 既能表"卡自触发"又能表"全局监听"，靠 codegen 上下文推断
- **拒绝原因**：
  - C# 方法签名不同（Self 收 `this`，Any 收 `exhaustedCard` 参数），命名应显式
  - 不区分 → validateGraph 没法拒绝"Card 节点图里塞 onAnyCardExhausted"

### 备选 E：Card trigger 表只保留 onPlay（最极简）

- **理由**：onPlay 覆盖 95% 卡，onSelfDraw 真实但低频，onSelfExhaust / onSelfDiscard 几乎不用
- **拒绝原因**：
  - 用户（grill 评审）明确表示**两种形态都要**——"卡自触发 + 全局监听都有真实用例"
  - 砍掉 onSelfExhaust / onSelfDiscard 等于放弃形态 1 的复合卡（升级版 Bash / 消耗触发类）

### 备选 F：EFFECT_KINDS 全部共享 + target 字段（走法 1）

- **理由**：单表最简，所有 effect 都用同一条 schema，`target` 字段决定 codegen 时谁接收
- **拒绝原因**：
  - `dealDamage` 的 target 有 `enemy/self/allEnemies/anyEnemy/eventTarget/randomEnemy` 6 种 — target 字段膨胀
  - 命名（`exhaustSelf` vs `exhaustEventTarget`）比 target 推断更清晰
  - codegen 看到 `exhaustEventTarget` 直接使用事件参数，看到 `exhaustSelf` 直接操作当前 Card — 不用看节点级 target 字段

### 备选 G：EFFECT_KINDS + forms 数组（走法 3）

- **理由**：forms 数组显式标记 effect 适用哪些实体 + 形态
- **拒绝原因**：
  - 大部分 effect 是全 forms，标 forms 数组等于无信息
  - 增加 `validateGraph` 检查负担（forms 匹配 entityType），但实际语义由 UI 守门更合适

### 备选 H：语义化 kind + 节点级 `target` 覆盖（v1.3 曾选，v1.14 推翻）

- **理由**：默认情况下使用 kind 的目标，同时允许单个节点临时改变接收者。
- **拒绝原因**：同一行为出现多种序列化方式，并允许 `{ kind: 'applyBuffToEventTarget', target: 'self' }` 之类互相矛盾的状态；AI、迁移、校验与 codegen 都必须解决优先级。v1.14 改为目标化 kind 是唯一表示。

### 备选 I：validateGraph 不加形态 2 effect 规则

- **理由**：靠 UI palette 过滤 + codegen 报错足够
- **拒绝原因**：
  - JSON 导入路径绕过 UI 过滤, 损坏数据可被持久化
  - validateGraph 是**所有路径共用的契约校验**, 应包含完整规则
  - Q7-2 评审明确选加规则

### 备选 J：新增并行的“节点版 Card”模型与编辑器

- **理由**：可以隔离 v0.9 开发，对现有表单编辑器影响较小。
- **拒绝原因**：会产生两套 CardData、状态管理、校验与持久化语义；用户无法明确同一张卡应在哪个编辑器中维护，AI 与文件导入也必须选择两条数据路径。后续合并成本高于原位升级。

### 备选 K：继续以名称或数组索引标识 Card

- **理由**：无需迁移现有数据，改动范围较小。
- **拒绝原因**：名称可变且可能重复，数组索引会随排序和删除变化；两者都不能稳定绑定行为图。以名称派生文件名还会在重命名后留下旧生成文件。

### 备选 L：每张 Card 只允许一个 trigger

- **理由**：图结构与 codegen 最简单。
- **拒绝原因**：无法表达同一张 Card 同时具有 `onPlay` 与 `onSelfExhaust` 等多个触发行为，与支持复合卡的目标矛盾。允许重复的同类 trigger 也不可取，因为会生成重复的 C# override 方法。

### 备选 M：多个 trigger 共享同一个 effect 节点

- **理由**：重复行为只维护一个节点，画布更紧凑。
- **拒绝原因**：effect 的 receiver 与触发上下文可能冲突，编辑共享节点会隐式改变多个触发方法，且 codegen 与形态校验必须处理多重归属。v0.9 采用独占分支；若未来出现强复用需求，应设计显式动作组，而不是用汇入边表达隐式复用。

### 备选 N：允许 effect 分叉并隐式决定执行顺序

- **理由**：一个节点可直接连接多个后续效果，图更自由。
- **拒绝原因**：C# 最终必须顺序执行，而边的插入顺序和画布坐标都不是可靠的领域语义。显式 `order` 虽可解决，但会扩大 v0.9 的 schema 与 UI；在 condition/branch 尚未落地前，线性效果链已经覆盖目标范围。

### 备选 O：Card 必须通过完整生成校验才能保存

- **理由**：磁盘中的 Card 始终可生成，状态最单纯。
- **拒绝原因**：用户无法安全保存只有 trigger、存在孤立 effect 或参数尚未填完的编辑中状态。项目源数据应忠实保存用户工作，生成产物则只代表最近一次通过完整语义校验的版本。

### 备选 P：为旧 Card 自动创建或推导行为图

- **理由**：迁移后更接近可生成状态，用户补录工作较少。
- **拒绝原因**：默认添加 `onPlay` 会擅自假定触发语义；从任意 C# 方法体部分推导节点则可能遗漏不可识别代码，让用户误认为迁移完整。空图迁移草稿诚实表达恢复边界，并保护旧 C# 不被过早覆盖。

### 备选 Q：一个动作同时保存草稿并生成 C#

- **理由**：按钮少，延续旧编辑器的“保存到项目”心智模型。
- **拒绝原因**：Card 草稿允许不完整，一个动作无法清晰表达“源数据已保存但暂不可生成”。v0.9 将草稿自动保存与显式生成拆开，分别反馈状态。

### 备选 R：Card 表单与行为图各自维护撤销历史

- **理由**：能最大程度复用现有 `useNodeGraph`，实现改动较小。
- **拒绝原因**：焦点无法可靠表达用户想撤销的最近操作；表单与行为图既属于同一 Card 文档，就应按真实编辑顺序进入同一历史。详见 ADR-0005。

### 备选 S：每次状态变化都记录一个完整 Card 快照

- **理由**：实现直接，无需定义合并事务。
- **拒绝原因**：连续输入和节点拖动会制造大量无意义步骤并迅速耗尽历史上限。v0.9 按用户交互事务合并，保持撤销粒度与真实意图一致。

### 备选 T：AI 结果直接应用或逐节点采纳

- **理由**：直接应用步骤少；逐节点采纳控制细。
- **拒绝原因**：直接应用会在预览前替换并自动保存草稿；逐节点采纳可能破坏图约束。v0.9 采用完整 AI 提案预览，确认后作为一个可撤销事务，详见 ADR-0002。

### 备选 U：AI 请求期间锁定 Card 或合并并发修改

- **理由**：锁定可消除冲突；三方合并可尝试同时保留用户与 AI 的变化。
- **拒绝原因**：模型等待期间锁定编辑体验差；图合并可能破坏结构和语义约束。v0.9 检测 revision 变化并将提案标为过期，详见 ADR-0002。

### 备选 V：允许生成或静默忽略空 trigger

- **理由**：其余完整分支仍可生成，空 trigger 可作为代码占位。
- **拒绝原因**：空 override 没有运行价值，而静默忽略会让图与 C# 不一致。v0.9 允许把空 trigger 保存为草稿，但生成校验要求每个 trigger 至少连接一个 effect。

### 备选 W：Card ID 使用 UUID、随机后缀或静默占位符

- **理由**：自动生成简单，冲突概率低，也能处理中文显示名。
- **拒绝原因**：ID 同时进入 C# 类名和文件名，可读性与可引用性重要。v0.9 采用用户在首次落盘前确认的代码标识符；无法从名称生成时明确要求输入，而不是静默产生不可读身份。

### 备选 X：删除 Card 时永久删除或保留活动 C#

- **理由**：永久删除实现简单；保留 C# 可以在误删时继续运行。
- **拒绝原因**：默认永久删除难以恢复，而活动 C# 残留会让游戏继续加载用户认为已删除的 Card。v0.9 把 Card 文档与生成产物一起移入项目内回收站。

### 备选 Y：允许删除过程留下 Card 文档与活动 C# 分离

- **理由**：底层文件操作失败时无需回滚，可标记“删除未完成”供后续修复。
- **拒绝原因**：用户可能看到 Card 已消失但游戏仍加载残留 C#。v0.9 通过回收站暂存、完整性校验与补偿恢复实现原子删除；失败时 Card 保持活跃。

### 备选 Z：未知 kind 作为普通草稿错误继续编辑

- **理由**：用户仍能修改已知属性和节点，不必等待升级应用或安装扩展。
- **拒绝原因**：旧版本自动保存可能重写或丢弃未知字段，已知节点编辑也可能破坏未知依赖。v0.9 对单张 Card 使用保真只读恢复，不阻塞项目内其他 Card。

### 备选 AA：旧 schema 只在内存迁移或整项目一次性升级

- **理由**：只在内存迁移不触碰原文件；整项目升级可保持版本完全一致。
- **拒绝原因**：内存迁移会在每次打开时重复，并迫使保存路径长期兼容两套表示；整项目升级会因一张坏 Card 阻塞全部数据。v0.9 逐 Card 备份后原子升级，失败则单独隔离。

### 备选 AB：用 revision、磁盘 C# 比较或内存 dirty 判断生成同步

- **理由**：revision 和 dirty 标记实现简单；比较 C# 内容无需额外元数据。
- **拒绝原因**：revision 会把节点移动误判为需重新生成，dirty 无法跨重启，草稿不可生成时也无法稳定比较 C#。v0.9 记录排除布局元数据的生成语义哈希。

### 备选 AC：生成同步只比较 Card 语义哈希或应用版本

- **理由**：只存一个值，判断简单；应用版本天然随发布变化。
- **拒绝原因**：只比较 Card 会漏掉模板/codegen 修复，应用版本又会让纯 UI 升级误触发重新生成。v0.9 以 sourceHash + 仅随生成逻辑变化的 generatorVersion 构成生成指纹。

### 备选 AD：批量生成要求全部成功或遇错即停

- **理由**：项目不会出现部分更新，控制流也更简单。
- **拒绝原因**：一张草稿、只读或失败 Card 会阻止其他正常 Card 更新过期产物。生成物按 Card 独立可重建，v0.9 采用逐项尽力完成并给出精确汇总。

### 备选 AE：任何非同步 Card 都阻止测试，或始终只警告

- **理由**：全阻止规则最简单安全；只警告则用户自由度最高。
- **拒绝原因**：未生成草稿本就不会被游戏加载，不应阻塞；但会加载的旧/失败产物若只警告，用户容易误测。v0.9 分级预检，区分“明确排除”与“危险不一致”。

### 备选 AF：忽略外部 C# 修改或反向导入

- **理由**：忽略符合生成产物可覆盖的严格模型；反向导入则尝试保留用户修改。
- **拒绝原因**：无提示覆盖可能丢失外部工作，反向导入又无法无损恢复行为图并违背单一权威源。v0.9 记录 artifactHash，发现变化后阻止并要求用户先备份/导出或确认重新生成。

### 备选 AG：v0.9 同时交付 Relic Any/EventTarget 链路

- **理由**：Self/Any 模型可在同一版本闭环，避免设计先于实现。
- **拒绝原因**：Card 端到端不依赖 EventTarget；捆绑会让 v0.9 被 Relic 运行时 API、额外 codegen 和集成验证阻塞。v0.9 不暴露半成品 kind，v0.10 再完整交付。

### 备选 AH：大分支一次合并或新旧 Card 编辑器长期双轨

- **理由**：大分支减少中间重构；双轨与功能开关可以逐步切流。
- **拒绝原因**：大分支难以定位回归，双轨会复制 Card 模型、Store、持久化与生成语义。v0.9 内部按纵向切片保持测试全绿，但只在完整链路就绪后对用户一次切换。

### 备选 AI：只凭单元测试发布，或要求三平台真实游戏全验收

- **理由**：前者发布快；后者发布信心最高。
- **拒绝原因**：只跑单测覆盖不了真实文件与 Electron 生命周期，而三平台/真实游戏/真实 LLM 又会不成比例地阻塞 v0.9。采用自动化数据安全 + 临时目录文件集成 + 核心手工 smoke test 的中间门槛。

## 关键发现

### 形态 1 vs 形态 2 不是 trigger 表的范围问题，是命名问题

grill 过程发现：用户说的"onDiscard / onExhaust 用例"实际上**两种形态都要**：
- 形态 1（卡自触发）：卡 X 自己被消耗时触发效果
- 形态 2（全局监听）：装备的 Relic 监听任意卡被消耗

如果不区分命名 → validateGraph 不知道 Card 节点图里能不能放形态 2 的 trigger → 跨实体污染。

加 `Self` / `Any` 前缀后 → 方法名携带语义 → C# 签名明确（Self 收 `this`、Any 收事件参数） → codegen 可机械翻译 → validateGraph 可机械校验。

### EFFECT_KINDS 共享的边界

`dealDamage / healHp / applyBuff / gainBlock` 这些 effect 是**通用副作用** — 不属于 Card 或 Relic 特有。卡打出时"对敌人造成 6 点伤害"与遗物"装备后每回合对敌人造成 6 点伤害"是**同一个 effect**，只是触发器不同。

**但**：`exhaustSelf` / `exhaustEventTarget` / `applyBuffToEventTarget` 等**目标绑定 effect** 不共享 — C# 方法签名与接收者不同，命名应显式区分。

这条原则同样适用于 v0.10+ 的 Potion / Enemy / Event：通用 effect 在 EFFECT_KINDS 大表里，实体绑定 effect 各占一条。

只有 trigger 是**实体绑定**的（每个实体有自己的事件时点），effect 是**通用副作用 + 实体绑定 effect 各占一条**的混合。

### EFFECT_KINDS 拆分 vs trigger 拆分的非对称

- **trigger**：完全靠 `entity` 字段分组（Card / Relic / Enemy / Event 各自的范围不重叠）
- **effect**：混合形态 — 通用副作用共享 + 实体绑定 effect 各占一条

非对称的原因：trigger 的"事件时点"是**每个实体独有的事实**（Card 没有 onCombatStart，Relic 没有 onPlay），effect 的"动作"是**通用副作用**加上**实体特异动作**（dealDamage 通用，但 exhaustSelf 是 Card 特有）。

### validateGraph 规则的扩展时机

v0.9 之前 `validateGraph` 不检查 trigger.entity，因为 Relic 是唯一实体类型，无跨实体需求。v0.9 加 Card 后，**第一次出现跨实体可能性**，必须加这条规则。

推后加 = v0.9 上线后发现"CardEditor 误显示 onCombatStart"再补 — 成本远高于一开始就有。

### effect 与 trigger 的 `entity` 字段非对称处理

- **trigger 的 entity 字段**：validateGraph 强校验（Card 节点图里出现 onCombatStart → 拒绝）
- **effect 的 entity 字段**：v0.9 对已注册 effect 校验其 entity/receiver 是否适用于当前 Card trigger 上下文；尚未交付的 EventTarget kind 不注册，因此输入中出现时按未知 kind 处理

理由：UI palette 过滤只能防止画布操作，不能保护 AI/导入路径；所有已注册 kind 都必须在生成校验中验证上下文。未来 v0.10 注册 EventTarget kind 时再启用对应 receiver 规则。

## 后果（Consequences）

### 正面

- **代码量净减**：Card 不需要独立 BFS / 独立 trigger 表 / 独立 validateGraph 规则集 — 共用层（`useNodeGraph` / `collectStatements` / `EFFECT_KINDS`）增加 ~10%，但 v0.10+ 加 Potion / Enemy 时几乎零增量。
- **AI JSON Schema 落地**（评审候选 5）：Card 节点图是 AI 输出的最大载体 — 提示词可写"为这张卡设计一个 trigger→effect 链"，AI 输出 JSON 走 `validateGraph` → `collectStatements` → `generateCardCode`。
- **codegen 测试可重用**：Card 的 codegen 测试可以借用 Relic 的 BFS 测试用例（只换 trigger 名称 + effect data）。
- **跨实体 trigger 不可能误用**：Card 图中的 Relic trigger 会被 validateGraph 拒绝；v0.9 未注册的 `onAnyCard*` 则作为未知 kind 拒绝。
- **effect 命名即语义**：`exhaustSelf` 与 `exhaustEventTarget` 是两个明确动作，codegen 机械翻译，不读取节点级通用 target。

### 负面

- **Card 表单 + 节点图并存**：CardEditor 同时有表单（name / cost / type / description）和节点画布。UI 层需要 tab 切换或上下分区 — CardEditor.tsx 文件会比 RelicEditor 复杂。
- **v0.9 只闭环 Card receiver**：Self/Owner effect 在本版验证；Relic Any/EventTarget 的运行时签名与 codegen 复杂度明确延后到 v0.10。

### 中性

- **entity 字段是单值还是数组**：当前是单值（`'card' | 'relic' | 'enemy' | 'event'`）。如果将来出现"Relic 与 Enemy 共享 trigger"（如 `onDeath`），改为数组即可 — 这是 v0.10+ 决策，v0.9 阶段保持单值。

- [ ] 草稿自动保存、离开前 flush、原子删除补偿、回收站恢复与 ID 冲突有测试
- [ ] AI 完整提案预览/确认/单步撤销、revision 过期检测有测试
- [ ] 批量生成报告与游戏测试预检各状态分支有测试
- [ ] 使用临时项目目录执行真实文件集成测试，不只 mock FileService
- [ ] 仓库只剩一份权威 CardData 与一个 CardEditor 入口，不存在长期双轨路径

- [ ] 新建 Card → 编辑表单/行为图 → 自动保存 → 重启恢复 → 显式生成 → 测试预检

### 不阻塞 v0.9 的扩展验证

- 真实游戏内行为验证
- Windows / macOS / Linux 三平台安装包全量实测

这些项目可在发布后继续验证，但不得替代上述自动化和手工数据安全门槛。

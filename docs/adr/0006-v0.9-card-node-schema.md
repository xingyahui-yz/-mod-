# ADR-0006：v0.9 Card 节点 schema — 完全同构 trigger→effect 链 + Self/Any 前缀命名

> 状态：已接受 · 日期：2026-08-12 · 来源：`/grill-with-docs` 评审（2026-08-12，v0.8 合 main 后）
> 适用范围：v0.9 "卡牌接入节点编辑器" 的节点 schema 形态；连带 v0.9 Relic trigger 列表扩展

## 背景（Context）

v0.8 完成架构清理（评审 5 候选 3/5 ✅）后，v0.9 起点评估指向 **E1 卡牌接入节点图**。现有节点编辑器（`useNodeGraph` + `kinds.ts` + `RelicEditor.codegen`）是事件驱动模型（trigger→effect 链），与卡牌的语义形态是否同构需要先敲定。

v0.7 / v0.8 时 Card 仍为纯表单 + 实时预览；Codegen 是文本字段级（`generateCardCode` 用 Mustache 渲染）。问题：

1. **是否复用 trigger→effect 模型** — Card 与 Relic 是不是同一种"事件驱动实体"？
2. **trigger 表怎么拆分** — 大表 / 分表 / 共享？
3. **trigger 列表范围** — Card 真需要哪些 trigger？
4. **"卡自触发" vs "全局监听"** — `onDiscard` / `onExhaust` 两种语义形态要不要都在 Card 表里？

## 决策（Decision）

### 1. 完全同构 trigger→effect 链

Card 复用 Relic 的节点图模型：

- 一个 Card = 一个 trigger 节点 + 0..N 个 effect 节点 + 边
- `useNodeGraph(cardId, 'card', initial?)` 与 `useNodeGraph(relicId, 'relic', ...)` 同形
- codegen 复用 `collectStatements` BFS 逻辑（v0.5.2 起已稳定），共用 `EFFECT_KINDS` 表
- 模板差异：Card 模板 `cardTemplate.mustache`，Relic 模板 `relicTemplate.mustache`

### 2. TRIGGER_KINDS 大表 + `entity` 字段（A1）

`src/node-editor/kinds.ts`（或新建 `src/shared/kinds.ts`）维护**一张大表**，每条 trigger 定义加 `entity: 'card' | 'relic' | 'enemy' | 'event'` 字段：

```ts
export const TRIGGER_KINDS = {
  // Card 形态 1（卡自触发）
  onPlay:           { entity: 'card',  label: '使用卡牌',     methodName: 'OnPlay' },
  onSelfDraw:       { entity: 'card',  label: '抽到自身',     methodName: 'OnSelfDraw' },
  onSelfExhaust:    { entity: 'card',  label: '自身被消耗',   methodName: 'OnSelfExhaust' },
  onSelfDiscard:    { entity: 'card',  label: '自身被弃',     methodName: 'OnSelfDiscard' },
  // Relic 已有（v0.5.2 起）
  onCombatStart:    { entity: 'relic', label: '战斗开始',     methodName: 'OnCombatStart' },
  onCombatEnd:      { entity: 'relic', label: '战斗结束',     methodName: 'OnCombatEnd' },
  onTurnStart:      { entity: 'relic', label: '回合开始',     methodName: 'OnTurnStart' },
  onTurnEnd:        { entity: 'relic', label: '回合结束',     methodName: 'OnTurnEnd' },
  // Relic v0.9 新增（形态 2 全局监听）
  onAnyCardExhausted:  { entity: 'relic', label: '任意卡被消耗', methodName: 'OnAnyCardExhausted' },
  onAnyCardDiscarded:  { entity: 'relic', label: '任意卡被弃',   methodName: 'OnAnyCardDiscarded' },
} as const
```

UI 层（`NodeGraphCanvas` 工具栏 + `useNodeGraph.addNode`）按 `entity` 字段过滤：CardEditor 看不到 Relic trigger，反之亦然。

### 3. Self / Any 前缀命名约定（关键）

**Self 前缀 = 形态 1（卡自触发）**：`onSelfDraw` / `onSelfExhaust` / `onSelfDiscard` — 触发器绑定到**这张卡自己**的行为。

**Any 前缀 = 形态 2（全局监听）**：`onAnyCardExhausted` / `onAnyCardDiscarded` — 监听器订阅**任意卡**的事件，由装备它的实体（Relic）响应。

无前缀（`onPlay` / `onCombatStart` / `onTurnEnd`）= 默认形态（按上下文自明）。

这个命名约定的语义价值：codegen 看方法名就知"有没有事件参数" — `OnSelfExhaust` 收 `this`，`OnAnyCardExhausted` 收 `exhaustedCard` 参数。

### 4. validateGraph 新规则

`validateGraph` v0.9 起加一条规则：

```ts
// trigger 的 entity 字段必须匹配 graph 的 entityType
if (node.type === 'trigger' && triggerDef.entity !== graph.entityType) {
  return { ok: false, reason: `Trigger '${kind}' 不允许用于实体类型 '${entityType}'` }
}
```

避免"CardEditor 里不小心拖入了 `onCombatStart` Relic trigger"这类跨实体污染。

### 5. codegen 复用粒度

`collectStatements(graph: NodeGraph): string[]` **完全共用**（BFS 从 trigger.out 出发，遍历 effect 节点，渲染 C# 语句）。

模板层差异（`cardTemplate.mustache` vs `relicTemplate.mustache`）由 `generateCardCode` / `generateRelicCode` 各自包装。

`EFFECT_KINDS` 表 100% 共享 — Card 的 `dealDamage` / `gainBlock` / `applyBuff` 与 Relic 同名同实现，因为这些 effect 是**通用副作用**，与实体无关。

## 备选方案（Alternatives Considered）

### 备选 A：Card 不接入节点图（v0.9 跳过）

- **理由**：Card 表单 + AI 生成已经覆盖 90% 真实用例，节点图 ROI 低
- **拒绝原因**：
  - "卡自触发"（形态 1）的复合卡真实存在（升级版 Bash 类、消耗触发类）
  - 评审候选 5（kinds registry 注入 validateGraph）的真正价值是 AI 输出节点图 — Card 不接入 = AI JSON Schema 失去最大载体
  - 跳过 Card 意味着 v0.9 仍要做 E5/E6 实体，它们与 Relic 完全同构，无新决策价值

### 备选 B：部分同构（只有 effect，无 trigger）

- **理由**：Card 触发统一 `OnPlay`，省去 trigger 节点；UI 更简单
- **拒绝原因**：
  - 失去"条件触发"表达力（onSelfDraw / onSelfExhaust 类卡无法表达）
  - 与 Relic 模型不同构 → codegen 不能共用 `collectStatements`（要写两份 BFS 逻辑）
  - 未来 v0.10+ 加 Potion / Enemy 时会重复同一纠结

### 备选 C：TRIGGER 表分表（relic/kinds.ts vs card/kinds.ts）

- **理由**：每个实体自治，文件隔离
- **拒绝原因**：
  - 加新实体时改 N 个文件（v0.10 加 Enemy 又新建 `enemy/kinds.ts`）
  - 共享 trigger（如 `onTurnEnd` 既能在 Relic 又能在 Enemy 用）要在 N 张表复制
  - "过早拆分"陷阱 — v0.9 阶段只有两个实体，看不出共享 trigger 需求

### 备选 D：形态 1 / 形态 2 不区分命名

- **理由**：`onExhaust` 既能表"卡自触发"又能表"全局监听"，靠 codegen 上下文推断
- **拒绝原因**：
  - C# 方法签名不同（Self 收 `this`，Any 收 `exhaustedCard` 参数），命名应显式
  - 不区分 → validateGraph 没法拒绝"Card 节点图里塞 onAnyCardExhausted"

### 备选 E：Card trigger 表只保留 onPlay（最极简）

- **理由**：onPlay 覆盖 95% 卡，onSelfDraw 真实但低频，onSelfExhaust / onSelfDiscard 几乎不用
- **拒绝原因**：
  - 用户（grill 评审）明确表示**两种形态都要**——"卡自触发 + 全局监听都有真实用例"
  - 砍掉 onSelfExhaust / onSelfDiscard 等于放弃形态 1 的复合卡（升级版 Bash / 消耗触发类）

## 关键发现

### 形态 1 vs 形态 2 不是 trigger 表的范围问题，是命名问题

grill 过程发现：用户说的"onDiscard / onExhaust 用例"实际上**两种形态都要**：
- 形态 1（卡自触发）：卡 X 自己被消耗时触发效果
- 形态 2（全局监听）：装备的 Relic 监听任意卡被消耗

如果不区分命名 → validateGraph 不知道 Card 节点图里能不能放形态 2 的 trigger → 跨实体污染。

加 `Self` / `Any` 前缀后 → 方法名携带语义 → C# 签名明确（Self 收 `this`、Any 收事件参数） → codegen 可机械翻译 → validateGraph 可机械校验。

### EFFECT_KINDS 100% 共享的边界

`dealDamage / healHp / applyBuff / gainBlock` 这些 effect 是**通用副作用** — 不属于 Card 或 Relic 特有。卡打出时"对敌人造成 6 点伤害"与遗物"装备后每回合对敌人造成 6 点伤害"是**同一个 effect**，只是触发器不同。

这条原则同样适用于 v0.10+ 的 Potion / Enemy / Event：它们的 effect 节点几乎肯定在 EFFECT_KINDS 大表里。

只有 trigger 是**实体绑定**的（每个实体有自己的事件时点），effect 是**通用副作用**（跨实体复用）。

### validateGraph 规则的扩展时机

v0.9 之前 `validateGraph` 不检查 trigger.entity，因为 Relic 是唯一实体类型，无跨实体需求。v0.9 加 Card 后，**第一次出现跨实体可能性**，必须加这条规则。

推后加 = v0.9 上线后发现"CardEditor 误显示 onCombatStart"再补 — 成本远高于一开始就有。

## 后果（Consequences）

### 正面

- **代码量净减**：Card 不需要独立 BFS / 独立 trigger 表 / 独立 validateGraph 规则集 — 共用层（`useNodeGraph` / `collectStatements` / `EFFECT_KINDS`）增加 ~10%，但 v0.10+ 加 Potion / Enemy 时几乎零增量。
- **AI JSON Schema 落地**（评审候选 5）：Card 节点图是 AI 输出的最大载体 — 提示词可写"为这张卡设计一个 trigger→effect 链"，AI 输出 JSON 走 `validateGraph` → `collectStatements` → `generateCardCode`。
- **codegen 测试可重用**：Card 的 codegen 测试可以借用 Relic 的 BFS 测试用例（只换 trigger 名称 + effect data）。
- **跨实体 trigger 不可能误用**：`Self` / `Any` 前缀让"Card 节点图里塞 onAnyCardExhausted"被 validateGraph 当场拒绝。

### 负面

- **Card 表单 + 节点图并存**：CardEditor 同时有表单（name / cost / type / description）和节点画布。UI 层需要 tab 切换或上下分区 — CardEditor.tsx 文件会比 RelicEditor 复杂。
- **trigger 列表不再对称**：Card 4 个（onPlay / onSelfDraw / onSelfExhaust / onSelfDiscard），Relic 7 个（含 2 个 Any 全局监听）。不是"两边都对齐" — 但这是真实需求差异，不应人为对齐。
- **`onAnyCardExhausted` 的 C# 签名复杂**：要传 `exhaustedCard` 参数进 `OnAnyCardExhausted(MyCardComponent card)`。codegen 渲染 effect 节点时，要从 effect.data 读 "对被消耗的卡做什么"，不是简单的 `DealDamage(6)`。这是 v0.9 codegen 唯一新增的复杂度。

### 中性

- **entity 字段是单值还是数组**：当前是单值（`'card' | 'relic' | 'enemy' | 'event'`）。如果将来出现"Relic 与 Enemy 共享 trigger"（如 `onDeath`），改为数组即可 — 这是 v0.10+ 决策，v0.9 阶段保持单值。

## 验证（Validation）

- [ ] v0.9 实施后：`useNodeGraph('card-1', 'card')` 与 `useNodeGraph('relic-1', 'relic')` 接口完全一致
- [ ] `validateGraph` 拒绝 `entityType='card'` 的图里出现 `onCombatStart` 节点
- [ ] `collectStatements` 在 Card 和 Relic 上输出格式一致（只有 trigger.methodName 不同）
- [ ] AI 生成 Card 节点图：JSON Schema 与 Relic 节点图同构（共享 `node.type` + `node.data.kind`）
- [ ] `EffectKind` 测试用例 100% 复用（dealDamage / gainBlock 等不重写）

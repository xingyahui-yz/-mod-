# AI 卡面、打击音效与人物动作：可行性与初步方案

日期：2026-09-26。依据当前工作区源码与当天查阅的第一方文档；工作区存在未提交开发内容，以实际源码为准。本文是方案，不表示已完成生成服务调用或游戏运行验证。

## 结论

建议投入，但按“游戏接入验证 → 公共素材基础 → 卡面 → 音效 → 角色动作”的顺序实施。

| 能力 | 判断 | 第一版范围 | 主要难点 |
| --- | --- | --- | --- |
| 卡面插画 | 高可行性，优先做 | 文生图、参考图变体、候选挑选、裁切、绑定卡牌 | 统一画风、构图适配、游戏资源路径 |
| 打击音效 | 高可行性，随后做 | 短音效生成、试听、裁切、音量调整、绑定具体攻击效果 | 起音、重复触发、伤害落点同步 |
| 人物关键姿势/短序列帧 | 有条件可行 | 单角色 idle / attack / hit；death 提供有效回退 | 外观连续性、透明背景、锚点和状态转换 |
| 高质量完整骨骼动画 | 不适合首版承诺全自动 | 后续支持导入人工整理的动画，逐步探索 AI 辅助 | 拆层、绑骨、权重、动作修正及运行时兼容 |

按本项目目标，默认“人物动作”指 STS2 战斗中的 2D 角色表现，不含 3D 动捕、长剧情视频。卡面第一版指插画；卡框、费用、名称和规则文字由程序/游戏排版，后续再开放卡框设计。

## 当前代码真正具备什么

1. **Card 文档和提案流程可复用。** `src/card/cardDocument.ts`、`cardCatalog.ts` 以及 `src/ai-conversation/` 已有单一文档、确认应用、revision 检查、历史和恢复机制。应复用这些规则，素材候选独立建模，不直接塞进严格的 Card 文本提案响应。
2. **图片目前只有字段。** `src/types/index.ts:23` 有 `imagePath?`，`src/card/fingerprint.ts` 纳入该路径；但 `src/components/CardEditor.tsx:969` 的预览未渲染图片，`src/card/card.mustache` 未生成图片资源绑定。更改同一路径下的文件内容也不等于更改当前源指纹。
3. **文件接口以文本为中心。** `electron/main.ts:110` 和 `:160` 使用 UTF-8 读写，`src/services/FileService.ts` 的写入参数是字符串。需新增受控二进制下载/导入、媒体检查、缩略图和预览能力。
4. **已有多服务商配置，但适配器输出仍是文本。** `src/services/llm/adapters/base.ts` 与 `httpAdapter.ts` 围绕文本响应、JSON 和默认 30 秒超时构建。不能仅替换模型名称来生成图片、音频或视频；须独立媒体适配器和任务状态。
5. **角色与声音领域尚未建立。** 目前主要是 Card/Relic；`src/shared/kinds.ts` 无音效播放、动画播放的现成类型。角色文档、状态绑定、动作预览都是增量工作。
6. **游戏运行闭环有缺口。** `src/components/NewProjectModal.tsx:79` 创建目录和简单 Godot/C# 脚手架，未生成完整 C# 工程与导出配置；`electron/main.ts:279` 主要查找并启动游戏可执行文件，`modPath` 未用于编译、打包或部署。`cardPreflight.ts` 检查 C# 产物同步，不验证游戏编译或资源包可加载。README 的“一键测试”不等同于完整构建部署。
7. **模板与当前框架文档存在差异。** 本地模板使用 `RitsuMod.Content` / `CardComponent`，而当前 RitsuLib 文档给出 `ModCardTemplate`、content pack 和资源 profile。尚未固定用户目标游戏/依赖版本，不据此断言所有旧模板必然无效，但必须先验证兼容性。[当前内容编写文档](https://sts2-ritsulib.ritsukage.com/guide/content-authoring-toolkit)

因此本次判断分两层：在桌面工具内生成、挑选和保存素材很可行；让素材随 Mod 正确运行，还要建立版本明确的导出、编译、打包和部署步骤。

## 已核实的游戏侧接入点

- 卡牌：当前 RitsuLib 提供 `CardAssetProfile.PortraitPath`，并有卡框等独立资源字段，可将插画与其他卡面元素分开。[Asset Profiles](https://sts2-ritsulib.ritsukage.com/guide/asset-profiles-and-fallbacks)
- 音效：`GameAudioService.Shared` 通过 `AudioSource` 接收事件或独立声音文件，并支持播放生命周期与重复播放冷却。第一版优先验证独立文件路线，再决定是否需要 FMOD bank。[FMOD And Audio](https://sts2-ritsulib.ritsukage.com/guide/fmod-and-audio)
- 动作：`VisualCueSet` 面向非 Spine 角色，支持命名姿势或帧序列；可通过自定义战斗动画状态机接入。官方说明要求视觉资源打入 PCK、使用 `res://` 引用并准备回退姿势。[Creature Visuals And Animation](https://sts2-ritsulib.ritsukage.com/guide/creature-visuals-and-animation)

这些是当前文档提供的可选入口，必须在选定游戏版本和相匹配的 RitsuLib 包上编译、运行确认，不能直接视为本项目已经具备。

## 三类功能的建议流程

### 卡面

输入卡牌名称、描述、元素、项目画风和可选角色参考图，生成 2–4 张候选；用户选择后裁切、调整焦点，预览卡面，再确认应用。候选数量为产品默认建议，需服从服务商数量和费用限制。

保存项目画风配置（配色、笔触、构图约束、参考资产），反复使用同一参考素材。AI 不绘制费用和规则文字。生成原图保留，裁切输出另存版本。输出尺寸与纵横比由阶段 0 确认的卡面槽位决定，不把模型的原始分辨率当作游戏标准。

第一期仅接一家图像供应商，并支持本地图片导入以独立验证素材链路。模型和供应商选择详见配套研究文档。

### 打击音效

输入材质（剑刃/拳击/火焰等）、强度、建议时长、单次/连击、混响与尾音，生成若干短候选。提供波形试听、前后静音裁切、短淡入淡出、音量和峰值检查；保留原始音频，导出 WAV 或经目标运行时验证的格式。

首版覆盖物理打击、斩击、魔法命中；不同时做配音和背景音乐。必须使用音效生成模型，不能拿 TTS 或音乐 API 代替。

声音绑定到稳定的效果节点 ID 和事件语义（如某次攻击命中），支持多个攻击节点使用不同声音。不要只在 `onPlay` 时统一播放，否则可能出现未命中先响、多段攻击重复叠音、AOE 音量爆炸。具体 hook 和实际伤害落点时序需要运行验证。

### 人物动作

分三档推进：

1. **关键姿势版：** AI 基于已选定角色参考生成 idle / attack / hit 等姿势，统一透明背景、画布、脚底锚点和朝向；应用内预览配合简单位移、缩放或受击闪白。游戏侧用 VisualCue 或已验证的场景/状态机转换。它是轻量动作表现，不承诺连续骨骼动画。
2. **短序列帧版：** 按单动作生成/导入帧，提供逐帧检查、删帧、帧率、循环、落点标记与对齐工具，输出帧序列/图集及运行时描述。先做一个角色三个动作，通过一致性验收再扩展 cast / death / relaxed 等。
3. **骨骼版：** 支持 Spine/Godot 等目标格式的人工制作素材导入；AI 辅助姿势和动作草稿。自动拆层、绑骨和权重另立研究任务。

文生视频只能作为动作参考或需要进一步处理的中间产物。抽帧后仍有背景、轮廓闪烁、服装/武器漂移、脚底滑动、首尾循环和受击中断问题；不以“生成视频成功”作为人物动作验收。

角色绑定应归属于 `CharacterDocument` 的外观/动作集合，卡牌只引用动作 cue，避免每张卡独立保存整套角色帧。

## 公共架构

对应的目标流程见 [AI 媒体创作与 Mod 导出目标流程（方案）](./diagrams/ai-media-generation-proposal.workflow.html)。该图表达未来目标，不代表仓库当前已具备媒体生成或完整游戏导出能力。

建议新增的职责边界（名称是方案建议）：

| 模块 | 责任 |
| --- | --- |
| `src/assets/` | AssetDocument、版本、引用、验证、候选与确认事务 |
| `src/media-generation/` | GenerationJob、能力路由、任务状态、费用记录与恢复 |
| `electron/media/` | Provider 请求、二进制流、凭据访问、下载、后处理子进程 |
| `src/character/` | 最小 CharacterDocument、动画集合、cue 和状态绑定 |
| `src/game-export/` | 目标版本、资源映射、构建清单、编译/打包/部署检查 |

React 只处理需求、进度和预览，耗时转码在 worker/子进程执行。首版沿用 Electron + React + TypeScript，无需自建账号后台、推理集群或本地模型部署。

### 数据与存储

- `AssetDocument` 保存类型、来源、模型、提示词、参考素材哈希、生成时间、输出参数、文件 SHA-256 与素材版本；授权来源信息可作为元数据记录。二进制文件与 JSON 分开，API Key 不写入项目。
- `GenerationJob` 保存项目 ID、目标实体和 revision、远端任务 ID、请求摘要、阶段、输出引用和可获得的费用数据。区分排队、运行、下载、待选择、失败、中断/结果未知；同步 API 同样包装成任务。
- 已确认实体绑定固定 `assetId + version`；接受/撤销沿用文档历史事务，素材版本保持不可变。只有当前引用、历史和未决提案都不再引用时，才能清理素材。
- `.modstudio/assets/` 保存元数据，`.modstudio/generation-jobs/` 保存任务，`assets/source/` 保存生成原件与候选；导出时只把实际引用的资源放进独立 staging 目录，映射为 `res://<ModId>/...`。游戏包不携带全部候选或生成记录。
- 新增素材引用应做 Card schema 迁移，兼容旧 `imagePath`，不长期保留两套权威绑定。`cardAiProposal.ts` 当前有固定 `schemaVersion: 2`，`conversationResponse.ts` 使用精确字段白名单，升级时须同步调整。普通文字 Card 提案没有媒体字段时，必须保留已有素材引用。

### 必须解决的工程问题

1. **能力独立配置：** 文本、图像、音效和未来动作可以来自不同模型；共享服务商账户资料不代表相同协议或密钥权限。媒体接口明确支持参考图、时长、输出格式、远端查询/取消等能力。
2. **任务恢复与费用：** 下载失败不重新生成；网络超时若结果未知，优先凭远端任务 ID 查询。服务不支持查询/幂等时提示未知并由用户显式重试，避免后台盲目重复付费。取消本地等待不等于供应商撤单或退款。
3. **项目隔离：** 任务始终绑定发起项目和实体；切换项目后不把结果写进新项目。目标已变化时保留候选并重新确认，不用旧结果覆盖新内容。
4. **二进制边界：** 限制文件尺寸、解码后像素/时长，检查实际媒体类型，流式下载并原子落盘。媒体路径只能在授权项目范围内解析，渲染端经受控预览协议访问；不沿用任意绝对路径作为素材 API。
5. **凭据：** 当前 `useAIStore.ts:178` 持久化 Key 与配置；新增媒体服务建议将凭据迁至主进程与系统凭据存储，界面仅持有 credential ID。迁移作为具体接入工作，避免 Key 进入项目或日志。
6. **构建可追踪：** 资源内容哈希、导出器版本和绑定关系纳入资源构建指纹，不能只比较路径字符串；预检增加缺失引用、格式、动画状态回退及打包资源检查。
7. **音画同步：** 命中时间使用经过验证的事件/时间标记；游戏伤害逻辑不等待云端生成。所有生成均在创作期完成，游戏仅播放本地素材。

## 实施阶段与验收

以下为一位熟悉 Electron/TypeScript 的开发者全职投入、云端 API 可用、优先一个目标平台的粗估；不是工期承诺。阶段 0 后重新估算，依赖版本迁移或 C# 导出器重做会增加工作量。

| 阶段 | 工作 | 粗估 | 验收条件 |
| --- | --- | --- | --- |
| 0 | 固定游戏与 RitsuLib 版本，用手工图片/音效/姿势验证运行时接口，列出模板差异 | 3–5 工作日验证窗口 | 样例 Mod 可构建并在游戏显示卡图、触发声音、切换姿势；否则先修兼容层并重估 |
| 1 | 最小素材库、二进制导入、任务基础与卡面生成闭环；接通卡图导出 | 8–12 工作日 | 生成/导入→预览裁切→确认→重开项目→构建→游戏显示；替换可撤销 |
| 2 | 短音效生成、试听后处理、效果事件绑定 | 5–8 工作日 | 单次/多段/多目标声音策略正确；重复任务可恢复，导出音效可播放 |
| 3 | 最小角色外观文档、姿势或序列帧编辑与状态机导出 | 10–20 工作日 | 一个角色 idle/attack/hit 可用，死亡有正确回退；攻击返回待机，受击可中断，音画一致 |

在阶段 0 不暴露重大重构的前提下，卡面+音效合计约 3–5 个开发周；加轻量角色动作约 5–9 周。高质量全自动骨骼动画不包含在该估算中。人工美术精修、额外平台和供应商审核等待另计。

验收测试重点：素材绑定迁移、陈旧候选、切项目、取消、任务恢复不重复生成、资源文件缺失、内容哈希、打包清单、音效多次命中和角色回退。已有 Vitest 可覆盖领域规则与 IPC 契约；真实 C# 编译、资源加载与游戏内动作仍需集成 smoke。

## 模型费用与实施决策

先采用用户自带 API Key，保留本地导入。只接一家图像服务和一家专用音效服务，人物动作第一版尽量复用图像服务生成关键姿势。具体 API 能力、候选服务与可核验价格见 [供应商研究](ai-media-provider-research-2026-09-26.md)。

预算按照“候选数量 × 单次生成价格 × 重试次数 + 后处理/存储”估计，不能用最终采用素材数量直接估价。界面设置单任务候选上限、项目预算提示和可用时的预估金额，实际账单以供应商返回或账户账单为准。

建议首个交付目标：选一张攻击卡，让用户从描述生成卡面和命中音效，挑选并确认，导出后在游戏里看到、听到。它能同时检验公共资产层和游戏导出层，并为角色动作留下明确扩展点。

# 下一步开发计划：把 Card 实机能力接入 Studio

本计划为建议方案。下一轮交付目标是：**用户在 Studio 编辑一张 Ironclad 攻击牌，完成生成、真实编译、部署、独立档测试和恢复测试前状态。**

## 已确认的基线

- 游戏：STS2 v0.111.0，Steam build ID 24724944；BaseLib v3.4.7。
- 独立实验已通过：真实 C# 构建、游戏初始化、实际 Ironclad 卡池成员及解锁查询、时间线/卡牌库恢复，以及初始牌测试中的 6 点实战伤害（HP 32→26，Block 0→0）。
- 仍待补验：普通战斗奖励或商店自然获取。初始牌和图鉴发现记录是用户指定的测试辅助手段，不计作自然获取证据。详见 [验收记录](./card-smoke-acceptance-2026-11-01.json)。
- 产品缺口：`src/card/card.mustache`、新项目模板仍使用 RitsuMod；`GameLauncher` 只做生成产物预检和启动，尚未真实构建、部署项目；`CardData` 尚无卡池归属。
- 当前游戏已恢复原版存档 1，0 个活动本地 Mod。原档 141 个文件和选择器校验不变，测试档及备份保留。计划制定不重新开启测试。
- 合并决策：用户已指定将本 Card 分支及其继承的 PR #4 改动整体合入 `main`；独立的 `codex/ui-design-refresh`、`codex/p5-ui-style` 和 `codex/ui-style-adjustment` 视觉分支暂不合并。执行前仍需确认远端 `main` 未变化。

## 实施顺序

### 1. P0：环境、路径和启动体验

交付：用户能明确配置游戏环境，识别安装包，并从正确入口启动游戏。

- 校验游戏目录包含实际 EXE/游戏数据，显示游戏版本和 Steam build ID；持久化配置，重启 Studio 后恢复。
- 分别检测 .NET SDK、运行时架构、BaseLib 及版本。使用已安装的可用工具；缺项显示检测结果和安装指引。
- Windows 启动通过 Steam 的应用启动方式传递 AppID，纳入当前裸 EXE 启动产生 `No appID found` 的回归场景。
- Mod 安装窗口明确区分游戏安装目标与待安装来源；显示所选来源路径、清单 ID/版本/作者和最终目标，识别游戏根目录、嵌套目录、缺清单等具体错误。
- 在关于/诊断信息中显示应用版本和构建提交，复核已有 `BaseLib.json` 修复为何仍曾显示“未知”。为本地依赖下载及目录构建产物补齐忽略规则。

完成条件：游戏路径在应用重启后仍有效；正确 BaseLib 包可识别并展示元数据；选错路径有可操作提示；通过应用启动不会出现缺少 AppID 的错误。

### 2. P0：生成可编译的 Card 包

交付：Studio 产出与已验证实验使用同一游戏 API 的项目和构建包。

- 新增明确的 Card 卡池归属，首批支持 Ironclad。同步文档校验、编辑器、AI 提案/上下文和序列化；旧 Card 保留数据，缺少归属时提示指定后再构建。
- 新项目骨架采用已验证的 .NET 9 DLL 构建方式，正确引用本机游戏和 BaseLib，生成带最低依赖版本的清单。首版沿用代码内本地化和游戏内卡图。
- 为当前 STS2 目标建立独立生成后端，先覆盖已经验证的“打出时对单个敌人造成伤害”。异步游戏命令、动态数值、内容注册和卡池归属作为完整生成契约。
- 为尚未迁移的节点、触发器、关键字和目标规则提供明确的预检错误，保留其源文档。共享节点定义中的旧 C# 输出不能同时带坏 Relic 生成器。
- 新增主进程构建服务：受控参数启动 SDK，返回退出码、编译诊断、产物路径/校验值，支持取消；构建结果绑定本次源数据，避免部署旧产物。

完成条件：至少两张不同 Card ID 的项目源数据能生成并真实编译，避免只复用固定样例；改变费用或伤害后，生成产物和构建记录同步变化；未支持的行为会阻止构建并定位到 Card/节点。

### 3. P0：部署、独立测试档与恢复

交付：把本次经过实测的隔离约束变成可重复操作的测试流程。

- 提供测试会话记录，保存开始前的 Mod 组合、部署归属、备份及原档校验值；部署前检测游戏已正常退出。
- 暂存并校验 Mod 包；对不属于当前项目的目标或相同 Mod ID 冲突明确报错。更新自己上次部署时保留可恢复版本。
- 通过游戏自身创建/选择独立测试档。Steam 云同步完成后才运行受保护的进度导入；本地复制文件不作为建档成功依据。
- 首次测试明确显示原档/测试档和解锁差异。“复制解锁进度”是可见的单独操作，受版本、档位、身份和文件校验约束；已有用户档位不被覆盖。
- “测试时加入初始牌”是可开关的测试辅助能力，限定到准备好的测试档；正式构建包不携带存档导入、初始牌注入或私有数据。
- “恢复测试前状态”只回退本会话管理的改动，恢复开始前的 Mod 组合。不能把本来就启用的用户 Mod 一并停掉；原档、测试档和备份均可保留。
- 将 `GameLauncher` 接为持续可见的步骤面板：环境检查 → 生成 → 构建 → 部署 → 启动/加载 → 实机验收。错误和日志可展开查看，实机状态由实际证据填写。

完成条件：应用内可准备/复用明确归属的独立测试档，进入游戏后核对路径和原档校验；菜单可用，测试辅助受控；恢复后实际进入测试前档案和 Mod 状态。构建失败、游戏未退出、目标冲突及云同步未就绪均可恢复重试。

### 4. 门禁：从编辑器到真实对局

交付：通过 Studio 自身的流程完成验收，形成可审阅的交付记录。

- 从编辑器把样例伤害从 6 改为另一固定值（例如 7），经生成、构建、部署后，在独立测试档实战核对相同伤害，证明修改确实进入了游戏。
- 关闭初始牌辅助，补一次普通奖励或商店自然出现/获取的证据，记录种子及出现位置。可与不启动游戏的构建链开发并行推进；未观察到之前，完整 Card 验收保持待完成。
- 为配置持久化、生成迁移、构建诊断/取消、真实文件系统部署冲突/回退、测试档身份隔离和包内容分别设置对应检查。
- 运行全量自动化、TypeScript/Electron 构建，以及本机 Windows 真实 C# 编译和手测。记录实际命令、数量和结果。依赖本机游戏程序集的检查单独标明；未执行不能显示为通过。
- 确认正式包只含预期 DLL/清单/资源，测试引导和存档资料不进入产物。
- 整理 Card 和归档功能的合并审阅记录；独立视觉风格分支保持在本次合并之外。

### 5. P1：卡面外观编辑（在 Card 构建链路打通后启动）

交付：用户可以在 Card 编辑器中生成或导入卡面图片，并在 Studio 和游戏实机中看到最终效果。

- 增加独立的卡面资源编辑区，区分风格参考图、生成结果和最终采用的卡面；参考图由用户提供，不隐式打包进 Mod。
- 接入 AI 图片生成操作，并使用 Studio 内置、版本化的固定风格提示词；将用户提供的原装卡牌图片作为本次生成的视觉参考，提示词明确要求匹配其画风，同时保留用户填写的卡牌主题/主体描述。
- 支持从本地手动导入卡面。生成或导入后均可预览、选择裁切/适配方式，并检查格式、尺寸、宽高比和文件大小；失败时保留上一个可用卡面。
- 在实现前先验证目标 STS2/BaseLib 版本接受的图像格式、资源路径和 Mod 打包/引用方式；把最终图片纳入项目序列化、构建和部署流程，确保正式包能在游戏内加载。
- 对 AI 生成明确显示所用参考图和当前提示词版本，由用户主动点击生成；参考图、临时图和生成失败产物不混入正式包。

完成条件：同一张 Card 可用用户参考图完成一次生成并能由用户挑选采用；手动导入路径独立可用；编辑器预览、重开项目后的资源引用、构建产物内容和游戏实机渲染均通过验证；切换或失败不会丢失原卡面。

## 首批提交建议

1. `fix(game-environment)`：游戏路径持久化、实际目录验证、Steam 启动、构建身份及 Mod 包反馈。
2. `feat(card-build)`：Card 卡池字段/兼容迁移、新骨架/生成后端、真实构建结果。
3. `feat(test-session)`：部署回退、独立档状态、测试辅助和恢复入口。
4. `test(card-e2e)`：应用内端到端及自然获取证据、完整检查和交接文档。

每批提交具有自己的完成条件。下一轮范围聚焦 Windows、已验证版本和 Ironclad 单体攻击，先交付完整可用链路，再扩展行为种类。

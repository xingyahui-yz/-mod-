> 状态：实施中；切片 1 已通过双重门禁，切片 2 已完成修复后首轮完整门禁并等待独立复检

## 1. 目标

把现有独立 AI 标签中的单次 Card 生成升级为每项目唯一、可恢复的多轮对话，同时保持当前项目源数据为唯一事实。

v0.10 完成后：

- 项目界面使用持续挂载、可折叠的右侧 AI 对话抽屉。
- 一轮可只回复文字，也可产生零到多个相互独立的 Card 创建/修改提案。
- 提案逐 Card 预览、接受、拒绝、过期、取代，并与 Card undo/redo 同步。
- 完整产品可见历史保存在版本化单 JSON 中；模型请求使用 token 预算、显式 Card 附件、一次自动补取和混合摘要。
- 失败、超时、取消、中断和重试均可审计，不保存 provider 原始响应、隐藏推理或认证信息。
- 对话达到容量阈值后可原子归档并重置；损坏或未知 schema 进入保真隔离。

## 2. 模块边界

新增 `src/ai-conversation/`，不放入 `src/card/`，也不抽象成通用 Entity Conversation。

```text
src/ai-conversation/
├── conversationDocument.ts      # 当前 v2 schema、严格解析与 v1 迁移入口
├── conversationMigrations.ts    # 逐版本纯函数迁移
├── conversationRepository.ts    # 路径、原子写、读回、备份、隔离、归档
├── conversationResponse.ts      # LLM 响应信封严格校验
├── conversationContext.ts       # 目录摘要、附件、token 预算、补取、混合摘要
├── projectConversation.ts       # 轮次/attempt/提案状态机与稳定 actions
├── ProjectConversationContext.tsx
├── ProjectConversationDrawer.tsx
└── *.test.ts(x)
```

边界规则：

- `useAIStore` 只保留跨项目 provider、API Key 和配置状态。
- 每个打开项目创建一个绑定 `projectPath` 的 `ProjectConversation` 实例，经 React Context 提供 selectors/actions；不导出全局 singleton 或内部 `setState`。
- `ConversationRepository` 接收最小文件端口：`readFile/writeFile/rename/mkdir/remove`。现有 `FileService` 只负责 Electron 接线，不承载对话业务规则。
- LLM adapter、时钟、ID 生成器和文件端口全部注入，测试不依赖 localStorage、真实网络或全局单例。
- `src/card/` 继续拥有 Card revision、结构/语义校验、提案原子应用和编辑历史；AI provenance 不进入 CardDocument 或生成指纹。

## 3. 共享协议与不变量

首切片直接使用可演进的响应信封，不建立临时文本接口：

```ts
interface ConversationResponseV1 {
  schemaVersion: 1
  text: string
  quickReplies: Array<{ id: string; label: string }> // 0..4
  proposals: [] // 切片 1 固定为空；切片 2 开放 CardProposal
}
```

- `text` 与 `quickReplies` 不得同时为空；quick reply ID 在本轮唯一，label 非空。
- 未知字段或任何非法 proposal 使完整响应失败，不保存或展示部分内容。
- 四个 provider 继续共享 `BaseLLMAdapter` 对话契约，不复制状态机。
- adapter 接受外部 `AbortSignal`。用户取消后迟到响应必须丢弃；超时是 `failed: timeout`，不混同 `cancelled`。
- 首次发送才创建 `.modstudio/ai/conversation.json`；展开抽屉不写空文件。
- provider 调用前必须原子保存用户消息和 `running` attempt。完整响应保存成功是唯一可见提交点。
- 最终保存失败不展示正文/快速回复，不缓存并延迟补写旧响应；重新打开时磁盘上的 `running` 转为 `interrupted`。
- “重试”保持原用户消息并追加 attempt；“修改后发送”创建新用户轮次。两者都读取最新项目基线。
- 项目切换必须先等待当前 attempt 完成，或由用户确认取消并完成持久化；旧请求不得后台完成或写入新项目。

## 4. UI 与上下文规则

- ≥1100px 时抽屉停靠在右侧，目标宽度约 360px并缩窄主编辑区；更窄窗口使用右侧覆盖层。
- 收起时保留窄入口和未读/运行状态点；有项目时跨标签持续挂载，无项目时禁用。
- 使用项目现有明暗主题，采用克制的蓝灰层次、清晰边框和少量半透明；密集消息、提案和差异区保持高对比、低装饰。
- AI 可返回 0..4 个快速回复。点击只填入输入草稿，不自动发送；编辑文字后取消选项关联。快速回复不能执行 Card 操作。
- 每轮始终提供全项目 Card 目录摘要；Card 全文必须由用户用 `@CardId` 或“添加上下文”显式附加。当前 Card 只是一键建议，不默认发送。
- 目录摘要默认包含 ID、名称、类型、稀有度、费用、关键词、截短描述、行为 kind 摘要和 revision；超预算时可见地降级为 ID、名称、类型和 revision。
- 显式附件优先且不可截断；连紧凑目录与最新消息都无法完整容纳时阻止发送。
- 每轮保存实际附加的 Card ID/revision、目录层级和 token 预算结果。

## 5. 交付切片与分支

每个切片使用独立短生命周期分支，通过自己的门槛后合并 `main`。所有提交保持编译和相关测试可运行，不提交“下一步再修”的破坏状态。

### 切片 1：零提案对话 walking skeleton

分支：`codex/v0.10-conversation-skeleton`

目标：最早贯通 UI、项目绑定、LLM seam、取消、恢复和 JSON 持久化。

建议提交序列：

1. `feat(ai-conversation): define response and conversation document v1`
   - 严格解析响应信封、消息、轮次、attempt、附件快照和诊断元数据。
   - 为未来 proposals/summary/archive 字段保留版本化演进点，不接受未知字段。
2. `feat(ai-conversation): add atomic conversation repository`
   - 固定活动/归档路径；真实文件原子替换、读回校验、逐版本迁移和保真隔离。
   - 首次写入失败不得产生 provider 调用。
3. `refactor(llm): add cancellable conversation request contract`
   - 四 provider 通过共享 base seam 支持对话信封与外部 `AbortSignal`。
   - 不在项目文档保存 raw response 或 credential。
4. `feat(ai-conversation): implement project-scoped turn state machine`
   - 发送、成功、失败、超时、取消、中断、重试、迟到响应和最终保存失败。
   - 每项目实例 + React Context + selectors/actions。
5. `feat(ai-conversation): add beta project conversation drawer`
   - 停靠/覆盖/收起、自适应、快速回复、显式 Card 附件、历史恢复。
   - 开发期保留并标记旧版单次 AI 标签，避免创建/修改能力回退。
6. `test(ai-conversation): close walking-skeleton release gate`
   - 完整自动化、TypeScript/Vite/Electron build；至少一个真实 provider 手工 smoke。

切片 1 验收：

- Repository 真实临时目录测试覆盖首次创建、原子替换、读回、迁移、损坏/未来 schema 隔离。
- 状态机覆盖发送前保存、成功、失败、超时、取消、迟到响应、重试、项目切换和最终保存失败。
- 组件覆盖抽屉形态、快速回复不自动发送、附件、历史恢复和隔离状态。
- fake adapter 覆盖共享 provider 契约；手工跑通“发送→回复→重开恢复”和“取消→重试”。

### 切片 2：逐 Card 提案与旧入口替换

分支：`codex/v0.10-card-proposals`

目标：达到旧 AI 创建/修改能力对等，并结束双入口阶段。

建议提交序列：

1. `feat(ai-conversation): validate card proposals in response v1`
   - 支持一轮 0..N 个 create/update Card 提案；禁止 delete 和引用未接受的新 Card。
2. `feat(ai-conversation): model per-card proposal lifecycle`
   - `pending/accepted/rejected/stale/superseded/reverted` 状态与事件验证。
   - 继续对话只取代被再次修改的同 Card pending proposal。
3. `feat(card): attach ai provenance to edit history transactions`
   - 接受修改形成一个 Card 历史步骤；undo 标记 reverted，redo 恢复 accepted。
   - provenance 不进入 CardDocument、语义 revision 或生成指纹。
4. `feat(ai-conversation): add atomic card proposal previews`
   - 现有 Card 定位并分区显示差异；新 Card 只读预览且不占 ID。
   - 修改直接整体接受并可撤销；新建确认最终 ID、实时校验冲突且不自动改名。
5. `feat(ai-conversation): add terminal rejection and feedback`
   - 拒绝二次确认、不可恢复；可选原因结构化保存并进入后续上下文。
6. `refactor(ai): remove legacy single-shot generator entry points`
   - 功能对等后同一提交删除 AI 标签、`generatedCards/proposal` 运行状态及旧平行调用入口。
   - `useAIStore` 仅保留 provider/API Key 配置。

切片 2 验收：每个状态转换、每 Card 独立过期、整 Card 原子接受、ID 冲突、拒绝不可恢复、undo/redo provenance、跨 Card 提案互不阻塞和旧入口删除均有接口/组件测试。

实施记录（2026-09-14）：响应与对话文档已升级为严格提案协议与 schema v2；提案按 Card 维护 `pending/accepted/rejected/stale/superseded/reverted`。修改接受作为单一 CardCatalog 历史事务，创建接受时才校验并占用最终 ID；右侧抽屉已接入逐 Card 差异预览、拒绝确认与过期重做。接受、撤销和重做使用 `transition → CardDocument → committed` 的可恢复跨文件协议，启动只续做最后一个未确认 transition；活动文件、回收站项目和合法后继优先于恢复日志。建议 ID 不进入项目命名空间，跨 Card 引用以请求时实际项目 revision 记录校验。Card autosave、生成指纹与提案事务共用逐 Card 串行文件写入和 revision 防护。旧 AI 页签、单次 Card 生成入口及平行 store 状态已删除。

第二遍修复记录（2026-09-14）：Card 历史事件同步获取 persistence barrier，后继自动保存等待每个 undo/redo 分别完成 `WAL → 该事件 Card → committed`，不会把 later snapshot 提前落盘；pending 建议 ID 不再遮蔽后来出现的真实项目 Card。创建提案和回收站恢复通过 no-replace 文件原语原子占用最终 ID，检查后的竞争文件不会被覆盖；同 ID 保存、创建、删除、恢复和迁移共用大小写不敏感的串行队列。项目切换在取消后重新核对 `requiresReload`，预保存结果不确定时同一次或后续确认都不能绕过恢复门禁。

### 切片 3：上下文智能与混合摘要

分支：`codex/v0.10-context-intelligence`

目标：让长对话在受控 token 预算内持续保持当前项目事实和用户意图。

建议提交序列：

1. `feat(ai-context): build deterministic detailed and compact catalogs`
2. `feat(ai-context): allocate token budget without truncating messages or attachments`
3. `feat(ai-context): allow one validated card context expansion per turn`
4. `feat(ai-context): derive proposal facts and rejection feedback locally`
5. `feat(ai-context): refresh llm intent summary after threshold`
6. `test(ai-context): cover budget boundaries and summary failure fallback`

关键约束：

- 最近消息从近到远整条纳入，始终保留最新用户消息，并预留输出及一次补取空间。
- 第一次模型调用可请求额外 Card ID；验证后最多再调用一次，第二次必须结束本轮。
- 提案状态、Card ID 和轮次事实由本地派生；LLM 只压缩用户目标与偏好。
- 摘要只在已完成轮次导致未摘要 token 越过阈值后后台刷新；失败保留旧摘要和未摘要消息，不阻塞对话。

### 切片 4：历史治理与 v0.10 发布收口

分支：`codex/v0.10-history-governance`

目标：完成容量治理、归档恢复、性能信号和最终 release gate。

建议提交序列：

1. `feat(ai-conversation): enforce soft and hard capacity thresholds`
   - 10 MB/5,000 消息软警告；50 MB/20,000 消息允许当前轮完成后阻止下一轮。
2. `feat(ai-conversation): atomically archive and reset active conversation`
   - 主动或硬限制归档均需二次确认、项目内写入和读回校验；旧 pending 提案失效。
3. `feat(ai-conversation): browse and export read-only archives`
4. `feat(ai-conversation): complete quarantine recovery workflows`
5. `perf(ai-conversation): measure load and atomic-save latency`
   - 为软阈值 p95>500ms、跨归档查询、局部/并发写和频繁硬上限等 SQLite 触发条件提供数据。
6. `docs(ai-conversation): close v0.10 release gate`

切片 4 验收：阈值边界、归档失败不重置、读回失败、只读归档、额外导出、隔离恢复、旧提案失效、性能记录与 Electron 手工 smoke 全部通过，随后在 README/CONTEXT 标记 v0.10 完成。

## 6. 回归与安全门槛

每个切片合并前必须：

- 运行受影响测试与完整 `npm test`。
- 通过 TypeScript、Vite 和 Electron 构建。
- 使用真实临时目录验证所有对话文档安全行为，不能只测内存 fake。
- 禁止组件或测试直接修改 conversation 内部 state；只经公共 actions/repository seam。
- 搜索确认没有项目对话写入 localStorage、没有 credential/raw response 进入项目文件、没有第二个活动对话入口。
- 保留用户现有 Card 编辑、自动保存、生成、回收站、批量生成和游戏预检行为。

## 7. 明确不在 v0.10 范围

- AI 删除 Card。
- 部分接受一张 Card 提案。
- 跨 Card 原子事务或未接受新 Card 的依赖图。
- 多段并行活动对话。
- SQLite 自动切换。
- Relic 或其他实体提案。
- 云端同步或服务端托管对话历史。
